# Внесение изменений (CONTRIBUTING)

Спасибо за интерес к ИСАР! Проект **публичный** (ядро — Apache 2.0), но процесс разработан под одного-двух сопровождающих, поэтому правила короткие.

## Основные принципы

- **Работаем через GitHub** — задачи, issues, PR.
- **Новые задачи заводятся только в GitHub Issues**, а не локальными `docs/issue-NN-…`. Детальная спека — в `docs/` с строкой `GitHub: https://github.com/dgabadulin/ArchRep/issues/N` (см. `docs/process-issue-tracking.md`).
- Документация проекта — в `docs/` (карта: `docs/README.md`).

## Как внести изменение

1. **Задача**: убедитесь, что issue заведён (или заполните [черновик issue](docs/github-issue-drafts/)).
2. **Ветка**: для изменения создайте feature-ветку от `main`:
   ```bash
   git checkout main && git pull && git checkout -b feature/kratkoe-imya
   ```
3. **Коммиты** — осмысленные, в стиле conventional:
   - `feat: ...` — новая функциональность
   - `fix: ...` — исправление
   - `docs: ...` — документация
   - `chore: ...` — служебное
   - `refactor: ...` — рефакторинг (без изменения поведения)
4. **Миграции БД** — всегда **два артефакта**:
   - `DB/scripts/*.sql` (прод, `psql`)
   - `DB/migrations/*.js` (demo, `node-pg-migrate`)
   — см. `.cursor/rules/db-migrations-dual.mdc` и `DB/README.md`.
5. **PR**: после пуша откройте Pull Request в `main` с описанием «что и почему», при необходимости закройте issue фразой `Closes #N`.

## Чего избегать

- Правок **только переводов строк** (LF↔CRLF) в не связанных с задачей файлах — засоряют историю.
- Кириллических имён файлов/каталогов.
- Публикации секретов: `.env.*` и локальные `deploy_*.bat` в репозиторий не попадают (см. `.gitignore`).
