# Decompose task (тимлид)

## Цель

План реализации и упорядоченные подзадачи. **Не кодировать**, пока пользователь не одобрит план.

## Предусловия

- Есть ответы аналитика / достаточно ясный issue / пользователь сказал «сразу план»
- Если критичные вопросы открыты — сначала `analyze-task`, не угадывать

## Шаги

1. Кратко зафиксировать **цель** и **ограничения** (из чата/issue).
2. Разложить по слоям, что затронем:
   - БД: `DB/scripts/*.sql` + `DB/migrations/*.js` (dual), если схема/данные
   - Backend: `backend/`
   - Frontend: `frontend-v3/`
   - Docs / параметры / конфиг
3. Список **подзадач** в порядке выполнения; отметить зависимости.
4. Для каждой подзадачи: ожидаемые файлы/зоны, критерий «готово».
5. Явно перечислить **out of scope**.
6. Указать **как проверить** после реализации (ручной чеклист + команды, если известны).
7. **Стоп**: «План выше. Реализуем после вашего ок.»

## Формат ответа

```markdown
## Цель
…

## План (по порядку)
1. … — файлы/слой — DoD подзадачи
2. …

## Развилки (если есть)
- A vs B → рекомендация: …

## Не делаем
- …

## Проверка после реализации
- [ ] …
```

## Согласование с репо

- Новые задачи — в GitHub Issues, не локальный «issue-NN»
- Перед кодом — ждать «ок / согласен / реализуй» (как в `github-issues`)
- Миграции — всегда оба артефакта (`db-migrations-dual`)

## Не делать

- Писать код «заодно с планом»
- Создавать PR
- Менять план молча после старта реализации — сначала обновить план и снова спросить, если scope сдвинулся
