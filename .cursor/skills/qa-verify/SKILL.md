# QA verify (тестировщик)

## Цель

Проверить уже сделанные изменения и дать отчёт. Не расширять scope «улучшениями», если пользователь не просил чинить найденное.

## Вход

- Утверждённый план / DoD / issue
- Diff или описание того, что реализовано (`git status` / `git diff` при необходимости)

## Шаги

1. Восстановить **критерии приёмки** из плана/issue (если нет — сформулировать минимальные и пометить как допущение).
2. Собрать **чеклист проверки** (UI-сценарии, API, миграции, регрессии).
3. По возможности **выполнить** проверки:
   - релевантные команды проекта (lint/test/migrate — только если уместны и безопасны)
   - просмотр кода на явные дыры относительно DoD
4. Зафиксировать: что проверено, что не удалось проверить (нет среды, нужны ручные клики).
5. Вердикт: **готово к вашему просмотру** / **нужны правки** (список).
6. PR/push/merge — **не** делать, пока пользователь явно не попросит.

## Формат ответа

```markdown
## Что проверяли
…

## Чеклист
- [x] …
- [ ] … (не проверено: причина)

## Находки
- …

## Вердикт
Готово к вашему просмотру | Нужны правки

## Рекомендуемый test plan для PR
- [ ] …
```

## Типичные риски ArchRep

- Миграция только в `scripts` или только в `migrations` (dual нарушен)
- Excel/списки: `excel=1` на API vs JSON-клиент `togafApi`
- Demo vs prod: параметр в `/api/config` после перезапуска API
- Скрытые/синтетические id на графе (bundle edges и т.п.)

## Не делать

- Реализацию новых фич под видом «раз уж тестируем»
- Объявлять merge без гейта пользователя
- Закрывать GitHub Issue без просьбы
