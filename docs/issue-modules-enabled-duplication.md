## Проблема

В MVP подключаемых модулей (`docs/modules-contract.md` §4.3) состояние «модуль включён» хранится в **трёх**
местах и вычисляется по неочевидному приоритету:

| Источник | Где | Приоритет |
|---|---|---|
| `ENABLED_MODULES` / `SYS_MODULE_<code>_ENABLED` | env | 1 (override) |
| `archrep.isar_modules.enabled` | таблица | 2 |
| `SYS_MODULE_<code>_ENABLED` | `ar_settings_parameters`, группа «Модули» | 3 |
| — | — | иначе `false` |

Реализация: `backend/modules/index.js` → `resolveEnabled()`.

Следствия:

- администратор включает модуль в «Настройки → Параметры», но модуль остаётся выключенным, потому что
  в `isar_modules` лежит `enabled=false` от прошлого запуска (и наоборот);
- одна и та же настройка правится в двух местах (таблица и параметр), значения расходятся;
- `npm run modules:status` вынужден печатать «источник: env|db|param» — сам факт подсказывает,
  что модель запутана;
- таблица задумывалась как «источник правды для UI» (§5), но UI её не читает:
  `GET /api/config.modules` собирается из памяти процесса (`getPublicModulesConfig()`),
  ключ лицензии берётся из env.

## Что таблица реально делает сейчас

1. аудит/снимок последнего запуска: `version`, `core_version`, `enabled`, `licensed`, `license_expires_at`;
2. второй по приоритету источник `enabled`;
3. добавляет коды в список кандидатов загрузчика (`extraCodes` в `registerModules`);
4. пишется при каждой попытке регистрации (`syncModuleRecord`).

Чего **не** делает: не хранит ключ лицензии, не влияет на `/api/config`, не влияет на монтаж
маршрутов, не даёт горячего включения (рестарт всё равно нужен), не хранит настройки модуля.

## Варианты

**A. Таблица = аудит (рекомендуется).** `enabled` считается только env → параметр → `false`;
`isar_modules` — read-only зеркало статуса (пишет ядро, читают админ/UI/поддержка).

- убирает двойной переключатель;
- сохраняет аудит и сроки лицензий (важно из-за офлайн-модели лицензий);
- остаётся основа для будущей страницы «Настройки → Модули».

**B. Таблица = основной переключатель.** `enabled` = таблица → env-override, параметр удалить.

- ближе к §5 контракта, задел на включение из UI без правки env;
- без UI правится только SQL; нужна миграция (удаление параметра).

**C. Убрать таблицу.** Статус только в памяти + `/api/config`, аудит — в логи.

- меньше сущностей, но теряются история и сроки лицензий; откат миграции; UI-страница усложняется.

## Предлагаемый объём работ (вариант A)

- [ ] `resolveEnabled()`: убрать ветку `dbRow.enabled`; приоритет env → параметр → `false`
- [ ] `backend/modules/registry.js`: комментарий «реестр = аудит/статус, не источник решения»
- [ ] `docs/modules-contract.md` §5: «источник правды для UI» → «журнал статуса + основа для UI»
- [ ] `docs/modules-contract.md` §16.7: зафиксировать решение (вариант A)
- [ ] `docs/modules-connect-checklist.md`, `docs/modules-admin-guide.md`: убрать способ «включить через
      `update archrep.isar_modules set enabled = true`», оставить env/параметр
- [ ] `backend/modules/__tests__/loader.test.js`: тест «строка `enabled=true` в реестре сама по себе
      не включает модуль»
- [ ] `scripts/modules-status.js`: в строке `enabled` больше не показывать источник `db`

## Критерии приёмки

- Включение модуля управляется **одним** способом (env или параметр БД), второй — только override.
- Значение `enabled` в `isar_modules` всегда равно фактически применённому (пишется ядром при старте).
- `npm run modules:status` не содержит источника `db`.
- Регрессия: `npm run test:modules` и `npm run check:routes` — зелёные.

## Связанное (вне scope этой задачи)

- **Лицензия проверяется только при старте**: `rec.licensed` фиксируется в памяти, `makeGate()`
  не пересчитывает статус. Истечение ключа в процессе работы не отключает модуль до рестарта,
  а `license_expires_at` в реестре становится неактуальным. Кандидат на отдельную задачу
  (периодическая перепроверка статуса, например раз в час, с обновлением строки реестра).
