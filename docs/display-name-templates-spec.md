# Спецификация шаблонов «видимого имени» для списков и селектов

## Цель

Сделать единый механизм управления тем, как сущности отображаются в:

- выпадающих списках форм (CRUD),
- модалках выбора связей,
- списках реестров и быстрых поисках.

Формат отображения задается через параметры в `Настройки -> Параметры`, без массового обновления данных в таблицах сущностей.

---

## Подход

1. Для каждого типа сущности задается шаблон отображения (display template) в параметрах.
2. На backend при выдаче списков вычисляется `display_name` по шаблону.
3. Frontend в списках/селектах показывает `display_name` (а не собирает строку самостоятельно).

Это снимает проблему денормализации и пересчета всех строк при смене формата.

---

## DSL шаблонов

### 1) Плейсхолдер поля

`{field_name}`

Пример:

- `{name}`
- `{code}`
- `{task_name}`

### 2) Условный блок

`[[ ... ]]`

Блок выводится только если все поля, использованные внутри блока, непустые.

Пустыми считаются:

- `null`
- `undefined`
- `''` (пустая строка после `trim`)

Непустые:

- `0`
- `false`
- любые непустые строки

### 3) Литералы и символы

Все остальные символы в шаблоне считаются литералом и выводятся как есть, например:

- пробелы, скобки, `||`, `->`, `:`, `,`.

### 4) Пример с условным разделителем

Требование: `<поле1> || '->' || <поле2>`, но если `поле2` пустое, не выводить `->`.

Шаблон:

`{field1}[[ || '->' || {field2}]]`

Результат:

- `field2 = null` -> только `field1`
- `field2 = "ABC"` -> `field1 || '->' || ABC`

Шаблон `{field1}[[ || '->' || {field2}]]`:

Параметры шаблонов должны применяться не только в CRUD-формах, но и для имен объектов в Анализаторе зависимостей:

- имена узлов графа (`AnalyticsView`, `AnalyzerGraph`);

## Валидация шаблонов

При сохранении параметра шаблона:

1. Проверять синтаксис:
   - корректность скобок `{}` и `[[ ]]`,
   - отсутствие вложенных `[[ ]]` (для простоты v1).
2. Проверять whitelist полей для конкретной сущности.
3. Если поле неизвестно — ошибка валидации.

## Контракт backend API

Для list endpoints, используемых в селектах, вернуть:

- `id`
- `display_name`
- (опционально) исходные поля, если нужны текущему UI

Пример ответа:

```json
{
  "id": 123,
  "code": "FIN01",
  "name": "АСУ Финансы",
  "display_name": "АСУ Финансы || (FIN01)"
}
```

## Производительность

### Почему должно быть быстро

- Форматирование строки выполняется в Node и дешево по CPU.
- Основная нагрузка обычно в SQL/сети, не в рендере строк.
- Шаблоны можно кэшировать и предкомпилировать в функцию.

### Когда нужна оптимизация

Если появятся длинные списки (десятки тысяч строк):

1. Пагинация/лимиты на API.
2. Кэш результата для справочников.
3. Опционально: материализованное `display_name` + триггеры.

---

## Обратная совместимость

- Если параметр шаблона не задан, использовать дефолтный шаблон в коде.
- Старое поведение UI сохраняется через эти дефолты.

---

## Риски и ограничения v1

- Нет функций форматирования (upper/lower/date) — только подстановка и условные блоки.
- Нет вложенных условий.
- Символы выводятся как литералы (что и требуется для `||`, `->`, скобок и пр.).

Этого достаточно для большинства бизнес-кейсов отображения в списках.
