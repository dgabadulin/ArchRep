# Сервисная операция: импорт данных в реестры

**Статус:** согласовано (открытых вопросов нет)  
**GitHub:** https://github.com/dgabadulin/ArchRep/issues/64  
**Пилот:** реестр веб-ресурсов (`ar_web_resources`)  
**Связанные материалы:** [web-resource-registry-schema.md](./web-resource-registry-schema.md), [access-control-design.md](./access-control-design.md) (RBAC **не реализован**), экран `SettingsServiceOperationsView.vue` (`/settings/service-operations`), [adding-new-entity-type.md](./adding-new-entity-type.md)

## 1. Назначение

Единая **сервисная процедура** массовой загрузки (и опционального обновления) записей в реестры ИСАР через Excel-шаблон, с построчной валидацией, частичной записью через сервисный слой сущностей и протоколом ошибок в том же формате файла.

Импорт **не** обходит бизнес-логику карточек: создание/обновление идёт через те же сервисы, что и UI форм (проекции метамодели, автокод, валидации).

## 4. Пользовательский сценарий

```text
Настройки → Сервисные операции
  → секция «Данные» → плитка «Импорт данных»
  → страница универсального импорта
       1) выбрать реестр / сущность (только с флагом «допустимо для импорта»; пилот: «Веб-ресурсы»)
       2) скачать шаблон Excel
       3) при необходимости — скачать текущий реестр (экспорт, как в списке сущности)
       4) заполнить файл → загрузить + опции
       5) «Проверить» и/или «Загрузить»
       6) итог: счётчики + скачать протокол (xlsx)
```

### 4.1. Страница «Сервисные операции»

- Существующие плитки (**Перезапустить API**, **Пересборка проекций потоков** и т.д.) **без изменений смысла**.
- Новая секция **«Данные»**, плитка **«Импорт данных»** → **«Открыть…»** → универсальная форма.

### 4.2. Универсальная страница импорта

Маршрут: `/settings/service-operations/import` (условно `DataImportView.vue`).

1. **Сущность** — select из типов с «допустимо для импорта».
2. **Скачать шаблон**.
3. **Скачать текущий реестр (экспорт)** — тот же код/API, что экспорт списка выбранной сущности.
4. **Файл** `.xlsx`.
5. **Опции** — §6 (в т.ч. состав протокола — §8).
6. **Проверить** / **Загрузить** / **Скачать протокол**.
7. Сводка: создано / обновлено / пропущено / ошибок.

## 5. Ключ сопоставления (пилот: веб-ресурсы)

**Только поле `code`.**

| Ситуация | Поведение |
| -------- | --------- |
| `code` пуст | **Создание**; `WR-…` выдаёт система при INSERT |
| `code` указан, в БД **нет** | **Ошибка строки** («код не найден; для создания оставьте code пустым») |
| `code` указан, в БД **есть** | По опции: `skip` / `update` / `fail`; **по умолчанию `update`**. При `update` — **только непустые** значения из строки (пустая ячейка не затирает поле в БД) |
| Upsert по URL / стенду / имени | **Нет** |

Типовой update: **экспорт** → правка → импорт с `code` и режимом `update`.

---

## 6. Опции проверки и загрузки

| Опция | По умолчанию | Описание |
| ----- | ------------ | -------- |
| Проверять обязательность | вкл. (всегда) | Пустые обязательные → ошибка строки (**для create**; при `update` пустая ячейка = «не менять», обязательность по пустым не валится) |
| Проверять дубли в файле | вкл. | Повтор непустого `code` в файле → ошибка |
| Проверять дубли в БД (строки без `code`) | выкл. | **Не искать**; всегда create |
| Если запись с `code` найдена | **`update`** | Также доступны `skip` / `fail`. При `update`: в DTO/сервис передаются **только непустые** поля строки |
| Состав протокола | **все строки** | Опционально сузить до ошибочных/пропущенных |
| Режим прогона | — | **Проверить** = ROLLBACK (§6.1); **Загрузить** = partial commit |

Дополнительно (всегда):

- формат URL, даты (`YYYY-MM-DD`);
- ссылки — **именами**; резолв → id по листам справочников; неизвестное/неоднозначное имя → ошибка строки;
- лимита числа строк нет (§2 п.13).

### 6.1. Режим «Проверить» (согласовано: A)

Общий **сервисный слой** сущности (тот же код, что за HTTP API формы). Импорт вызывает create/update **in-process**.

- **Проверить:** BEGIN → прогон строк → **`ROLLBACK`**; протокол с `would_create` / `would_update` / `error`.
- **Загрузить:** partial commit (savepoint на строку или транзакция на успешную строку).

Побочный эффект: «дыры» в `WR-…` после «Проверить» (`nextval` не откатывается) — **принято**.

## 7. Шаблон и экспорт Excel (правила для **всех** сущностей)

### 7.1. Заголовки

- Формат: **подпись формы/грида** + `(техническое_имя)`. Пример: `Краткое наименование (short_name)`.
- При расхождении форма↔грид эталон = **форма**; сначала унифицировать UI, затем Excel.
- Парсер смотрит на имя в скобках (или `_meta`).

### 7.2. Порядок колонок

| Зона | Содержание | Импорт |
| ---- | ---------- | ------ |
| Крайний слева | **`ID (id)`** записи | Не заполнять (игнор); в экспорте заполнен |
| Далее (основные) | Текст, даты, **имена** связей | Заполняет пользователь |
| Справа | Сырые FK (`ar_systems_id`, …) | Не заполнять (игнор) |

Импортёр **не** пишет id/FK из файла — резолвит ссылки по именам.

### 7.3. Резолв id по именам

Имена как на листах справочников файла / в БД. Не найдено / >1 совпадение → ошибка строки.  
Для ИС и модулей в Excel: только **`name`** (без `Родитель → …`); имя модуля в данных — вид **`система.модуль`**.

### 7.4. Excel Data Validation («Проверка данных»)

Генерация шаблона и экспорта — **ExcelJS**: для колонок-ссылок — список из диапазона листа справочника. Сервер при импорте всё равно валидирует имя по БД.

### 7.5. Симметрия экспорт ↔ импорт

**Экспорт = тот же пакет, что шаблон** (заполненные строки «Данные» + актуальные справочники + `_meta` + Data Validation), чтобы сценарий «экспорт → правка → импорт» сохранял выпадающие списки.

### 7.6. Пример: веб-ресурсы (пилот)

Порядок: `ID` → бизнес-поля → FK id справа. `template_version = 2`. Имя ИС/модуля — поле `name` (`система.модуль` для модулей).

---

## 8. Протокол результата

xlsx = исходные колонки + `row_no`, `import_status`, `import_error`.

Состав строк протокола — **опция** (§2 п.15):

- **по умолчанию:** все строки исходного файла со статусом;
- альтернатива: только `error` / `skipped` (и аналоги dry-run).

UI: «Создано N, обновлено M, пропущено K, ошибок E» + скачать протокол.

## 9. Архитектура

```text
SettingsServiceOperationsView (секция «Данные»)
  → DataImportView
       → GET  /api/import/entities     (флаг import_allowed / «допустимо для импорта»)
       → GET  /api/import/template
       → GET  экспорт реестра          (тот же, что у списка сущности)
       → POST /api/import/validate     (ROLLBACK)
       → POST /api/import/apply        (partial)
```

Каталог полей — §9.2–9.4 в прежней редакции смысла: конфиг колонок на backend; при новом поле сущности — обновить каталог + bump `template_version`; память процесса — чеклист + Cursor rule `entity-field-import-export.mdc`.

Флаг «допустимо для импорта» в пилоте: колонка (или аналог) в **`ar_metamodel_entity_types`**, UI в справочнике типов сущностей; сид: `web_resource` = true.

### 9.1. Каталог сущностей

| entity_code | Название в UI | Импорт |
| ----------- | ------------- | ----- |
| `web_resource` | Веб-ресурсы | да (`import_allowed`) |
| `gap` | Архитектурный долг | да |
| `adr_principle` | Принципиальные ADR | да |
| `principle` | Принципы | да (ключ `name`) |
| `technology` | Технологии | да (ключ `name`) |
| `system` | Информационные системы | да (ключ `code`, ручной) |
| `organization_unit` | Орг. единицы | да (ключ `name`) |
| `actor` | Заинтересованные лица | да (ключ `name`) |
| `business_service` | Бизнес-сервисы | да (ключ `name`) |
| `business_function` | Бизнес-функции | да (ключ `name`) |
| `domain` | Домены | да (ключ `name`) |
| `applied` | Прикладные ADR | нет (вложенная модель) |
| … | справочники / integration_flow | нет |

Реализация адаптеров: `backend/importEntities/`. Общий раннер: `backend/importLib/`.

### 9.2. Что такое «каталог полей» на backend

Это **не** UI и **не** лист Excel, а **машинное описание колонок** сущности на сервере, по которому backend:

1. строит шаблон (заголовки, порядок, справочники, dropdown);
2. выравнивает экспорт;
3. парсит файл (колонки по `(field)`);
4. резолвит имя → id и собирает DTO для сервиса сущности.

Фронт универсальной формы схему колонок не знает. Реализация: модуль/JSON/БД — на этапе кода.

### 9.3. При добавлении поля к сущности

Каталог сам не обновляется. Чеклист: форма/API/грид → **каталог полей** → сервис → bump **`template_version`** (обязательное новое поле → отказ старых файлов без колонки; необязательное — можно принять с пустым значением). См. также [adding-new-entity-type.md](./adding-new-entity-type.md) §7.

### 9.4. Как не забыть синхронизировать каталог

Память — в репозитории: чеклист `adding-new-entity-type.md`, правило `.cursor/rules/entity-field-import-export.mdc`, якорь-комментарий в коде каталога, критерий в issue/PR.

## 10. Права и аудит

**RBAC не реализован** ([access-control-design.md](./access-control-design.md)). Пилот без ролей — доступ как у прочих сервисных операций.

Аудит пилота: время, entity, файл/hash, режим, опции, счётчики; пользователь — после появления auth.

Целевые права после RBAC (не в пилоте): `service_operations:execute`, при необходимости `import:web_resource` / `web_resource:write`.

## 11. Вне пилота

- Наполнение импортом прочих реестров (флаг в пилоте уже есть; контент каталога полей — по мере подключения).
- Дедуп не по `code`.
- All-or-nothing на весь файл; удаление из файла; SQL в обход сервиса; async; лимит строк.

**В пилоте:** контракт Excel; **ID слева**; резолв по `name`; Data Validation (ExcelJS); экспорт = шаблон+данные; флаг import_allowed; секция «Данные».

## 12. Критерии готовности пилота

- [ ] Секция «Данные», плитка «Импорт данных»; старые операции на месте.
- [ ] Универсальная страница; select только с «допустимо для импорта»; веб-ресурсы доступны.
