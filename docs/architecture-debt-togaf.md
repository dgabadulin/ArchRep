# Учёт архитектурного долга в соответствии с TOGAF

## Связь с TOGAF

В TOGAF архитектурный долг (и технический долг как его часть) учитывается через:

- **Gap Analysis** (фазы B/C/D ADM) — разрывы между Baseline и Target Architecture.
- **Requirements** — невыполненные или частично выполненные требования (в т.ч. нефункциональные).
- **Constraints** — ограничения, несоблюдение или отложенное соблюдение которых создаёт риски и долг.
- **Work Packages** — пакеты работ по устранению разрывов и реализации целевого состояния.

То есть долг не вводится отдельной сущностью, а **отображается комбинацией** Gap, Requirement, Constraint и связей с архитектурными артефактами (системы, процессы, решения).

## Использование существующей метамодели

В документе [togaf-metamodel-implementation.md](togaf-metamodel-implementation.md) уже предложены сущности, достаточные для учёта долга:

| Концепция TOGAF | Сущность в репозитории | Роль в учёте долга |
|-----------------|------------------------|----------------------|
| Gap             | **ar_gaps**            | Разрыв «как есть» ↔ «как должно быть» по архитектуре (приложение, данные, технология). |
| Requirement     | **ar_requirements**    | Требование (в т.ч. НФТ), не выполненное или выполненное с отклонениями → долг. |
| Constraint      | **ar_constraints**     | Ограничение (регуляторное, техническое, организационное), нарушение или отложенное соблюдение = долг. |
| Work Package    | **ar_work_packages**   | Пакет работ по устранению разрыва/требования; привязка к плану и срокам. |
| Связи           | **ar_metamodel_relations** | Связь долга с системой, процессом, ADR, capability и т.д. |

Рекомендуемая модель: **архитектурный долг = зафиксированный Gap или невыполненное/частично выполненное Requirement или нарушенное/отложенное Constraint**, с опциональной привязкой к Work Package для планирования устранения.

## Расширения для явного учёта долга (опционально)

Чтобы явно маркировать и агрегировать «долг», без выхода за рамки TOGAF, можно ограничиться справочниками и атрибутами.

### 1. Категория долга (Gap / Requirement)

- В **ar_gaps**: справочник **ar_gap_types** с полем `code`, например:
  - `architecture_debt` — архитектурный долг (отклонение от целевой архитектуры);
  - `technical_debt` — технический долг (устаревшие решения, качество кода/инфраструктуры);
  - `compliance_gap` — разрыв соответствия (регуляторика, стандарты).
- В **ar_requirements**: поле **category** или справочник типов требований — выделить категорию «долг» (например, `debt_reduction`) для требований, фиксирующих необходимость погашения долга.

### 2. Атрибуты для приоритизации и отчётности

Для **ar_gaps** (и при необходимости для **ar_requirements**) добавить:

| Атрибут            | Тип         | Описание |
|--------------------|-------------|----------|
| impact_level       | varchar/int | Влияние (критический / высокий / средний / низкий) или код справочника. |
| remediation_effort | varchar     | Оценка усилий (например, S/M/L или человеко-дни) — опционально. |
| target_date        | date        | Желаемая дата устранения. |
| ar_work_package_id | bigint FK   | Ссылка на пакет работ по устранению (если есть таблица ar_work_packages). |

Для **ar_constraints** при необходимости:

- **violation_severity** — критичность нарушения (информационно о «долге» по соблюдению ограничения).

### 3. Связи через ar_metamodel_relations

Типы связей для долга (добавить в **ar_metamodel_relation_types** при использовании универсальной модели):

- `gap_affects` — Gap касается сущности (system, technology, process, data_entity).
- `requirement_concerns` — Requirement относится к сущности.
- `constraint_applies_to` — Constraint применяется к сущности.
- `work_package_resolves` — Work Package устраняет Gap / реализует Requirement.

Примеры:

- Gap «Дублирование учёта в системах A и B» → связи `gap_affects` к двум системам.
- Requirement «Привести API к стандарту REST» → связь `requirement_concerns` к системе или к группе систем.
- Work Package «Миграция с платформы X» → связь `work_package_resolves` к соответствующему Gap.

## Процесс учёта (рекомендуемый)

1. **Выявление**  
   В рамках архитектурных обзоров, ADR и анализа интеграций фиксировать:
   - разрывы (Gap) между текущим и целевым состоянием;
   - невыполненные или частично выполненные требования (Requirement);
   - ограничения (Constraint), по которым есть нарушения или отложенное соблюдение.

2. **Регистрация**  
   Заносить записи в **ar_gaps**, **ar_requirements**, **ar_constraints** и при необходимости связывать их с артефактами через **ar_metamodel_relations** (система, технология, процесс, ADR и т.д.). Указывать категорию/тип долга и приоритет.

3. **Планирование**  
   Создавать **ar_work_packages** для устранения выбранных разрывов/требований и связывать пакеты с соответствующими Gap/Requirement. Заполнять целевые даты и оценку усилий.

4. **Отчётность**  
   Отчёты и дашборды строить по:
   - списку Gap/Requirement с фильтром по типу «долг» и по статусу;
   - связям с системами/процессами (какой долг к чему привязан);
   - Work Package (что запланировано к погашению и в какие сроки).

Такой подход остаётся в рамках TOGAF (Gap, Requirement, Constraint, Work Package) и позволяет и учитывать архитектурный долг, и привязывать его к целевой архитектуре и планам реализации.
