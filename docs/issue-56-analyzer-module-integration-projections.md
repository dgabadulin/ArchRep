# Модульные проекции интеграций для Анализа зависимостей

GitHub: https://github.com/dgabadulin/ArchRep/issues/56

## Проблема

Сейчас интеграционные потоки подмешиваются в анализатор как связи `system -> system`.  
При построении графа от узла `subsystem` такие связи часто не попадают в инцидентные, поэтому пользователь не видит интеграции на уровне модулей.

Дополнительно есть требование корректного поведения при сворачивании модулей в родительскую систему.

## Цель

Обеспечить отображение интеграций в графе для сценариев:

- `module -> system`
- `system -> module`
- `module -> module`

и сохранить корректную семантику направления при наличии двух отдельных встречных потоков.

## Принципы решения

1. Источник истины по потокам остается `archrep.ar_integration_flows`.
2. Каждая запись `ar_integration_flows` - это одно направленное ребро.
3. "Встречное" направление моделируется отдельной записью в `ar_integration_flows` (не как флаг двунаправленности).
4. В граф передаются не эвристики UI, а явные направленные проекции в `archrep.ar_metamodel_relations`.
5. Пересборка проекций выполняется через существующую сервисную операцию в меню "Сервисные операции".
6. Фронтенд анализатора загружает связи **только** из метамодели (`loadAllRelations` → `togafApi.relations`), без отдельного вызова `/api/integration-flows`.

## Модель данных (целевая)

### 1) Типы связей в `ar_metamodel_relation_types`

Завести направленные типы для модульной проекции интеграций с явными ОТ/К.

С учетом текущей кодификации (`integration_flow`, `system_module`, `module_technology`, `system_technology`) использовать `snake_case` и префикс `integration_flow_`:

- `integration_flow_system_module` - "Интеграционный поток (Система -> Модуль)"
  - `from_entity_type_id = 1` (`system`)
  - `to_entity_type_id = 11` (`subsystem`)
- `integration_flow_module_system` - "Интеграционный поток (Модуль -> Система)"
  - `from_entity_type_id = 11` (`subsystem`)
  - `to_entity_type_id = 1` (`system`)
- `integration_flow_module_module` - "Интеграционный поток (Модуль -> Модуль)"
  - `from_entity_type_id = 11` (`subsystem`)
  - `to_entity_type_id = 11` (`subsystem`)

Примечания:

- Базовый тип `integration_flow` (`system -> system`) сохраняется для обратной совместимости.
- Направление ОТ/К фиксируется в типе связи и не интерпретируется на UI эвристически.

### 2) Определение типа конца (system/subsystem)

Дополнительные поля в `ar_integration_flows` не требуются: оба конца уже ссылаются на `ar_systems`, где модуль определяется по иерархии (`parent_*` не `NULL`).

На этапе построения проекции:

- если `parent_* IS NULL` -> конец считается `system`;
- если `parent_* IS NOT NULL` -> конец считается `subsystem`.

Отсюда автоматически получаются все нужные комбинации:

- `system -> system`
- `system -> subsystem`
- `subsystem -> system`
- `subsystem -> subsystem`

### 3) Изменение иерархии системы

Если объект в `ar_systems` меняет иерархический статус (например, был модулем, стал самостоятельной системой), записи в `ar_integration_flows` остаются корректными по FK, но типы концов в проекциях (`from_entity_type` / `to_entity_type`) могут устареть.

Поэтому спецификация фиксирует два допустимых режима:

1. **Минимальный (текущий):** после изменений иерархии запускать сервисную пересборку проекций из меню "Сервисные операции".
2. **Автоматический (рекомендуемый):** добавить синхронизацию при `AFTER UPDATE OF parent_*` на `ar_systems` для потоков, где `changed.id` участвует как source/target.

Оба режима совместимы; автоматический снижает риск "устаревшей" метамодели между изменением и ручной пересборкой.

## Пересборка проекций

Расширить текущую функцию пересборки проекций интеграций так, чтобы она:

1. Удаляла только проекции интеграций (как и сейчас, без затрагивания прочих relation types).
2. Пересоздавала:
   - базовые `system -> system` проекции (обратная совместимость),
   - модульные проекции для доступных комбинаций (`module -> system`, `system -> module`, `module -> module`).
3. Сохраняла идемпотентность и предсказуемые ключи/связь с источником (`reference_to_baserow`).

UI-кнопка в "Сервисных операциях" должна продолжить работать с этой расширенной пересборкой.

## Правила отображения на графе

1. При выборе модуля (`subsystem`) граф должен показывать инцидентные интеграции на уровне модуля согласно проекциям.
2. При выборе системы - поведение не регрессирует: видны связи системы, включая унаследованные/проецированные при необходимости.
3. При сворачивании модулей в систему:
   - концы ребер от `subsystem:*` переназначаются на родительский `system:*`;
   - дубликаты после переназначения схлопываются по ключу `(source, target, label)`;
   - направление ребра сохраняется.

## Критерии готовности

- В БД заведены типы связей для модульных интеграционных проекций с валидными ОТ/К.
- Проекция корректно определяет тип конца через состояние `ar_systems.parent_*` на момент синхронизации.
- Обновлена функция пересборки проекций и задействована в существующей сервисной операции.
- Для двух встречных интеграций в `ar_integration_flows` на графе отображаются два раздельных направленных ребра.
- На графе подтверждены сценарии `module -> system`, `system -> module`, `module -> module`.
- При сворачивании модулей ребра корректно поднимаются к родительской системе без потери направления.
- Нет регрессии для текущих интеграций `system -> system`.

## Реализация в репозитории

- **БД:** `DB/scripts/migrate_issue56_integration_flow_module_projections.sql` — типы связей, уникальный индекс по `reference_to_baserow` для всех `integration_flow*`, `upsert`/`rebuild`, триггер на `ar_systems` при смене `parent_ar_systems_id`.
- **BFF:** защита POST/PUT/DELETE `/api/togaf/relations` для всех кодов проекций потоков (`integration_flow`, `integration_flow_system_module`, `integration_flow_module_system`, `integration_flow_module_module`) при непустом `reference_to_baserow`.
- **Фронт:** `frontend-v3/src/api/graphApi.js` — `loadAllRelations` только из метамодели.
- **Документация по миграции:** `DB/README.md` (раздел Issue #56).

## Вне scope

- Полный редизайн UI анализатора.
- Миграции/правки для несвязанных relation types.
