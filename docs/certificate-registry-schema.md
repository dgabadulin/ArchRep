## 1. Назначение

Добавить в ИСАР реестр сертификатов с:

1. отдельной таблицей, API, списком и формой редактирования;
2. автогенерацией кода сертификата;
3. проекциями связей в метамодель по FK;
4. периодическими email-уведомлениями об **истечении** срока сертификатов через Job Runner (§6);
5. периодическими email-уведомлениями о **размещении** сертификата (заполнена «Ссылка на размещение») через Job Runner (§7).

## 2. Состав атрибутов

Реестр сертификатов должен содержать следующие поля:

| Поле | Тип | Обязательность | Комментарий |
|------|-----|----------------|-------------|
| `code` | string | да (системное) | Автогенерация на backend: `CRT-<номер>` без лидирующих нулей |
| `ar_domains_id` | FK -> `ar_domains` | да | Домен, для которого выпущен сертификат |
| `ca_ar_partners_id` | FK -> `ar_partners` | нет | Сертификационный центр |
| `issued_at` | date | да | Дата выпуска |
| `expires_at` | date | да | Дата окончания |
| `wildcard_flag` | boolean | нет | Признак wildcard |
| `placement_url` | text | нет | Ссылка на размещение, без строгой URL-валидации |
| `responsible_ar_employees_id` | FK -> `ar_employees` | нет | Ответственный сотрудник |
| `placement_notified_at` | timestamptz | нет (служебное) | Когда последний раз отправлено уведомление о размещении (§7) |
| `placement_notified_url` | text | нет (служебное) | Значение `placement_url`, по которому уже уведомляли (§7) |

Дополнительно:

- `id`, `created_at`, `updated_at` — технические поля;
- код не вводится пользователем вручную;
- при создании записи код формируется автоматически и сохраняется в БД;
- поля `placement_notified_*` не отображаются в форме и не редактируются пользователем.

## 3. Правила генерации кода

Формат кода:

```text
CRT-1
CRT-2
CRT-3
...
```

Требования:

- без лидирующих нулей;
- генерация на стороне backend / БД, а не во frontend;
- код уникален;
- пользователь не должен иметь возможности подменить код в форме создания/редактирования.

Допустимые варианты реализации:

1. sequence + `BEFORE INSERT`;
2. вычисление через отдельную служебную sequence без привязки к `id`;
3. генерация в backend перед insert с опорой на sequence в БД.

Предпочтительно: **sequence + trigger/default на стороне БД**, чтобы избежать гонок.

## 5. Проекции связей в метамодель

Нужно добавить связи по FK через PostgreSQL trigger и `ar_metamodel_relations`.

### 5.1. Связь сертификат -> домен

- код relation type: `certificate_domain`
- имя: `Выпущен для`
- направление: `certificate -> domain`
- источник: `ar_certificates.ar_domains_id`

### 5.2. Связь сертификат -> сотрудник

- код relation type: `certificate_employee_responsible`
- имя: `Ответственный`
- направление: `certificate -> employee`
- источник: `ar_certificates.responsible_ar_employees_id`

### 5.3. Поведение триггера

По аналогии с существующими FK-проекциями:

- `INSERT` / `UPDATE`:
  - удалить старые проекции сертификата по соответствующему типу связи;
  - вставить актуальные, если FK заполнен;
- `DELETE`:
  - удалить связанные проекции;
- выполнить backfill для уже существующих строк.

Рекомендуемый `payload`:

```json
{"projection":"fk","source":"ar_certificates.<field_name>"}
```

для соответствующего FK-поля.

## 6. Уведомления об истечении сертификатов

Использовать механизм, уже реализованный в [#68](https://github.com/dgabadulin/ArchRep/issues/68).

### 6.1. Новые параметры

Создать параметры БД:

| Код | Тип | Значение по умолчанию | Назначение |
|-----|-----|------------------------|------------|
| `CHK_CERT_EXPIRATION` | number | `30` | Порог в днях до окончания сертификата |
| `CHK_CERT_EXPIRATION_EMAIL` | string | пусто | Получатель(и) email-уведомлений |

### 6.2. Новое job

Добавить job:

- `code`: `certificate_expiration_check`
- `name`: `Проверка сроков сертификатов`
- `handler`: `certificate_expiration_check`
- `interval_seconds`: `259200`
- `enabled`: `true`

### 6.3. Правила отбора

Логика отбора должна быть **как у доменов**:

- `expires_at IS NOT NULL`
- `expires_at >= CURRENT_DATE`
- `expires_at <= CURRENT_DATE + CHK_CERT_EXPIRATION`

Поведение:

- уже истёкшие сертификаты не включать;
- сертификаты без даты окончания пропускать;
- если список пуст — письмо не отправлять;
- если email не задан — письмо не отправлять, но run помечать как `success` с понятным сообщением;
- повторные уведомления на следующих циклах допустимы.

### 6.4. Состав письма

В уведомлении выводить:

- домен;
- код сертификата;
- дату окончания;
- ответственного.

Формат письма — аналогично уведомлениям об истекающих доменах: text + html.

## 7. Уведомления о размещении сертификата

**Подход:** периодическое задание Job Runner (вариант B из обсуждения), **не** отправка внутри HTTP create/update.

**Назначение:** при появлении или изменении непустого поля «Ссылка на размещение» уведомить **ответственного за сертификат** о выпуске/размещении и перечне ИС, опубликованных на домене сертификата.

### 7.1. Согласованные бизнес-правила

| № | Тема | Решение |
|---|------|---------|
| 1 | Когда отправлять | `placement_url` непустой **и** (`placement_notified_url` IS NULL **или** `placement_notified_url <> placement_url`) |
| 2 | Создание с URL | Да — попадает в очередь на ближайший цикл job |
| 3 | Пустое → непустое | Да |
| 4 | Смена URL (`url1` → `url2`) | Да — повторное уведомление |
| 5 | Повторное сохранение без смены URL | Нет |
| 6 | Очистка `placement_url` | Письмо не отправлять; `placement_notified_*` не сбрасывать автоматически (при повторном заполнении URL сравнение с `placement_notified_url` снова определит необходимость письма) |
| 7 | Веб-ресурсы | Только со статусом **`published`** (`ar_web_resource_statuses.code = 'published'`) и `ar_domains_id` = домен сертификата |
| 8 | Отображение ИС | **Корневая ИС** + **модуль в скобках**, если веб-ресурс привязан к модулю (`ar_systems.parent_ar_systems_id IS NOT NULL`) |
| 9 | Получатель `To` | Только **ответственный за сертификат** (`responsible_ar_employees_id` → `ar_employees.email`) |
| 10 | IT-ответственные | Только **в теле письма** (колонка таблицы), не в `To`/`Cc` |
| 11 | Нет IT-ответственного / нет email у IT | Строку ИС **всё равно показывать**; в колонке IT — «—» |
| 12 | Нет ответственного за сертификат или нет его email | Письмо **не отправлять** для этой записи; в `result_json` run — `skip_reason`; fallback на `CHK_CERT_PLACEMENT_EMAIL` (§7.2) |
| 13 | Пустой список WR/ИС | Письмо **отправлять** (сертификат размещён, опубликованных веб-ресурсов на домене нет) |
| 14 | Дедупликация ИС в таблице | По паре (корневая ИС, модуль) + веб-ресурс (несколько WR на одну ИС — отдельные строки или одна строка с перечислением URL — на усмотрение реализации, предпочтительно **одна строка на WR**) |

### 7.2. Параметры БД

| Код | Тип | Значение по умолчанию | Назначение |
|-----|-----|------------------------|------------|
| `CHK_CERT_PLACEMENT_INTERVAL_SECONDS` | number | `86400` | Периодичность проверки (интервал между **успешными** запусками), в секундах. Пример: `86400` = 1 сутки, `259200` = 3 суток. Минимум при чтении — **3600** (1 час). |
| `CHK_CERT_PLACEMENT_EMAIL` | string | пусто | **Fallback:** получатель, если у ответственного за сертификат нет `email` (один адрес или несколько через запятую) |
| `CHK_CERT_PLACEMENT_EMAIL_ADD` | string | пусто | **Дополнительные получатели** (копия): рассылка дублируется на заданный список адресов (например, руководители). Несколько адресов через запятую. Не заменяет основного получателя. |

**Периодичность и `ar_jobs.interval_seconds`:**

- в `ar_jobs` для задания `certificate_placement_notify` задаётся **стартовое** `interval_seconds` (= `86400`);
- при расчёте «пора ли запускать» Job Runner для этого `code` использует **эффективный интервал** = `CHK_CERT_PLACEMENT_INTERVAL_SECONDS` из параметров (если параметр пустой или некорректный — `ar_jobs.interval_seconds`);
- изменение периодичности администратором — через параметр в настройках, без правки кода.

### 7.3. Задание Job Runner

| Поле | Значение |
|------|----------|
| `code` | `certificate_placement_notify` |
| `name` | `Уведомления о размещении сертификатов` |
| `handler` | `certificate_placement_notify` |
| `interval_seconds` | `86400` (дефолт; см. §7.2) |
| `enabled` | `true` |

Отображается в **Настройки → Управление заданиями** (история run, ручной запуск, вкл/выкл) — как `certificate_expiration_check`.

### 7.4. Цепочка данных для тела письма

```text
ar_certificates.ar_domains_id
  → ar_domains
  → ar_web_resources (ar_domains_id, status = published)
  → ar_systems (ar_systems_id)
      → корневая ИС: COALESCE(parent, self)
      → модуль: имя дочерней записи, если parent IS NOT NULL
      → it_lead_employee_id → ar_employees (ФИО для колонки «Ответственный от ИТ»)
```

Связь домен ↔ веб-ресурс — по FK `ar_web_resources.ar_domains_id` (реестр веб-ресурсов, #63/#67). Отдельной логики для `wildcard_flag` не требуется: сертификат привязан к записи домена в `ar_domains`, веб-ресурсы отбираются по тому же `ar_domains_id`.

### 7.5. Отбор сертификатов к уведомлению

Условие для одной записи `ar_certificates`:

```sql
trim(coalesce(placement_url, '')) <> ''
AND (
  placement_notified_url IS NULL
  OR trim(placement_notified_url) <> trim(placement_url)
)
```

После **успешной** отправки письма по сертификату:

```sql
placement_notified_at = now(),
placement_notified_url = placement_url  -- фактическое значение на момент отправки
```

Если отправка не удалась (SMTP) — `placement_notified_*` **не** обновлять; повтор на следующем цикле.

### 7.6. Получатели письма

1. **Основной `To`:** `ar_employees.email` ответственного за сертификат.
2. Если email пустой — **`To`** = адреса из `CHK_CERT_PLACEMENT_EMAIL` (если параметр тоже пуст — пропуск записи).
3. **`Cc`:** адреса из `CHK_CERT_PLACEMENT_EMAIL_ADD` (если заданы), **дополнительно** к п.1–2 (дублирование для руководителей).

Один сертификат — **одно письмо** (не пакетная сводка по нескольким сертификатам), в отличие от `certificate_expiration_check`.

### 7.7. Состав письма

**Тема (пример):** `[ИСАР] Размещён сертификат: {domain_name} ({code})`

**Шапка:**

- код сертификата;
- домен;
- даты выпуска и окончания;
- wildcard (да/нет);
- сертификационный центр (если есть);
- **ссылка на размещение** (`placement_url`).

**Таблица «ИС, опубликованные на домене»:**

| Корневая ИС | Модуль | Веб-ресурс | URL публикации | Ответственный от ИТ |
|-------------|--------|------------|----------------|---------------------|
| ERP | (модуль CRM) | Портал | https://… | Иванов И.П. |

- если модуль отсутствует — колонка «Модуль»: «—»;
- если IT-ответственный не указан — «—»;
- если веб-ресурсов со статусом `published` нет — текст: «На домене нет опубликованных веб-ресурсов».

Формат: text + html (как §6.4).

### 7.8. Результат run (`result_json`)

Рекомендуемые поля summary:

- `certificates_pending` — сколько записей попало в отбор;
- `emails_sent` — сколько писем отправлено;
- `skipped_no_recipient` — пропущено (нет ответственного и fallback);
- `certificate_ids` — id обработанных с успешной отправкой;
- `errors` — при частичных сбоях SMTP.

## 9. Критерии готовности

### Реестр и истечение (базовый scope #69)

1. Есть реестр сертификатов в БД, API и UI.
2. Код `CRT-N` генерируется автоматически и уникален.
3. Поля `Домен`, `Дата выпуска`, `Дата окончания` обязательны.
4. Созданы relation types и trigger-синхронизация связей:
   - `certificate -> domain`
   - `certificate -> employee`
5. Job Runner выполняет `certificate_expiration_check` раз в 3 дня.
6. Созданы параметры `CHK_CERT_EXPIRATION` и `CHK_CERT_EXPIRATION_EMAIL`.
7. Email об истечении содержит домен, код сертификата, дату окончания и ответственного.

### Уведомления о размещении (§7)

8. Колонки `placement_notified_at`, `placement_notified_url` добавлены dual-миграцией.
9. Параметры `CHK_CERT_PLACEMENT_INTERVAL_SECONDS`, `CHK_CERT_PLACEMENT_EMAIL`, `CHK_CERT_PLACEMENT_EMAIL_ADD` созданы.
10. Job `certificate_placement_notify` виден в UI заданий; периодичность управляется параметром §7.2.
11. При новом/изменённом `placement_url` ответственный получает письмо с URL размещения и таблицей ИС (только WR `published`, формат корневая ИС + модуль).
12. `CHK_CERT_PLACEMENT_EMAIL_ADD` дублирует рассылку на заданные адреса.
13. Реализация оформлена dual-миграцией для prod и demo.

## 10. Замечания по реализации

- Поскольку у сущности добавляются поля, список, форма и экспорт, при реализации нужно синхронизировать контракт импорта/экспорта с каталогом полей backend.
- Механизм уведомлений следует максимально переиспользовать по аналогии с `backend/domainExpiration.js` и `backend/certificateExpiration.js`.
- Для проекций связей лучше использовать ту же технику и именование trigger-функций, что уже применено в реестре доменов и веб-ресурсов.
- Новый модуль: `backend/certificatePlacementNotify.js` (рабочее имя).
- Handler: `backend/jobs/handlers/certificatePlacementNotify.js`.
- SQL: `certificates_select_pending_placement_notify` + join web_resources/systems/employees.
- API create/update сертификата **не** вызывает SMTP; только job обновляет `placement_notified_*`.
