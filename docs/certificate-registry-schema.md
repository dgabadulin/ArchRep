# Реестр сертификатов и уведомления об истечении

**GitHub:** https://github.com/dgabadulin/ArchRep/issues/69

**Связанные материалы:** [domain-registry-schema.md](./domain-registry-schema.md) (#67), [job-runner-design.md](./job-runner-design.md) (#68), [process-issue-tracking.md](./process-issue-tracking.md).

**Статус:** согласовано к реализации.

---

## 1. Назначение

Добавить в ИСАР реестр сертификатов с:

1. отдельной таблицей, API, списком и формой редактирования;
2. автогенерацией кода сертификата;
3. проекциями связей в метамодель по FK;
4. периодическими email-уведомлениями об истечении срока сертификатов через Job Runner.

---

## 2. Состав атрибутов

Реестр сертификатов должен содержать следующие поля:

| Поле | Тип | Обязательность | Комментарий |
|------|-----|----------------|-------------|
| `code` | string | да (системное) | Автогенерация на backend: `CRT-<номер>` без лидирующих нулей |
| `ar_domains_id` | FK -> `ar_domains` | да | Домен, для которого выпущен сертификат |
| `ca_ar_partners_id` | FK -> `ar_partners` | нет | Сертификационный центр |
| `issued_at` | date | да | Дата выпуска |
| `expires_at` | date | да | Дата окончания |
| `wildcard_flag` | boolean | нет | Признак wildcard |
| `placement_url` | text | нет | Ссылка на размещение, без строгой URL-валидации |
| `responsible_ar_employees_id` | FK -> `ar_employees` | нет | Ответственный сотрудник |

Дополнительно:

- `id`, `created_at`, `updated_at` — технические поля;
- код не вводится пользователем вручную;
- при создании записи код формируется автоматически и сохраняется в БД.

## 3. Правила генерации кода

Формат кода:

```text
CRT-1
CRT-2
CRT-3
...
```

Требования:

- без лидирующих нулей;
- генерация на стороне backend / БД, а не во frontend;
- код уникален;
- пользователь не должен иметь возможности подменить код в форме создания/редактирования.

Допустимые варианты реализации:

1. sequence + `BEFORE INSERT`;
2. вычисление через отдельную служебную sequence без привязки к `id`;
3. генерация в backend перед insert с опорой на sequence в БД.

Предпочтительно: **sequence + trigger/default на стороне БД**, чтобы избежать гонок.

## 5. Проекции связей в метамодель

Нужно добавить связи по FK через PostgreSQL trigger и `ar_metamodel_relations`.

### 5.1. Связь сертификат -> домен

- код relation type: `certificate_domain`
- имя: `Выпущен для`
- направление: `certificate -> domain`
- источник: `ar_certificates.ar_domains_id`

### 5.2. Связь сертификат -> сотрудник

- код relation type: `certificate_employee_responsible`
- имя: `Ответственный`
- направление: `certificate -> employee`
- источник: `ar_certificates.responsible_ar_employees_id`

### 5.3. Поведение триггера

По аналогии с существующими FK-проекциями:

- `INSERT` / `UPDATE`:
  - удалить старые проекции сертификата по соответствующему типу связи;
  - вставить актуальные, если FK заполнен;
- `DELETE`:
  - удалить связанные проекции;
- выполнить backfill для уже существующих строк.

Рекомендуемый `payload`:

```json
{"projection":"fk","source":"ar_certificates.<field_name>"}
```

для соответствующего FK-поля.

## 6. Уведомления об истечении сертификатов

Использовать механизм, уже реализованный в [#68](https://github.com/dgabadulin/ArchRep/issues/68).

### 6.1. Новые параметры

Создать параметры БД:

| Код | Тип | Значение по умолчанию | Назначение |
|-----|-----|------------------------|------------|
| `CHK_CERT_EXPIRATION` | number | `30` | Порог в днях до окончания сертификата |
| `CHK_CERT_EXPIRATION_EMAIL` | string | пусто | Получатель(и) email-уведомлений |

### 6.2. Новое job

Добавить job:

- `code`: `certificate_expiration_check`
- `name`: `Проверка сроков сертификатов`
- `handler`: `certificate_expiration_check`
- `interval_seconds`: `259200`
- `enabled`: `true`

### 6.3. Правила отбора

Логика отбора должна быть **как у доменов**:

- `expires_at IS NOT NULL`
- `expires_at >= CURRENT_DATE`
- `expires_at <= CURRENT_DATE + CHK_CERT_EXPIRATION`

Поведение:

- уже истёкшие сертификаты не включать;
- сертификаты без даты окончания пропускать;
- если список пуст — письмо не отправлять;
- если email не задан — письмо не отправлять, но run помечать как `success` с понятным сообщением;
- повторные уведомления на следующих циклах допустимы.

### 6.4. Состав письма

В уведомлении выводить:

- домен;
- код сертификата;
- дату окончания;
- ответственного.

Формат письма — аналогично уведомлениям об истекающих доменах: text + html.

## 8. Критерии готовности

1. Есть реестр сертификатов в БД, API и UI.
2. Код `CRT-N` генерируется автоматически и уникален.
3. Поля `Домен`, `Дата выпуска`, `Дата окончания` обязательны.
4. Созданы relation types и trigger-синхронизация связей:
   - `certificate -> domain`
   - `certificate -> employee`
5. Job Runner выполняет `certificate_expiration_check` раз в 3 дня.
6. Созданы параметры `CHK_CERT_EXPIRATION` и `CHK_CERT_EXPIRATION_EMAIL`.
7. Email содержит домен, код сертификата, дату окончания и ответственного.
8. Реализация оформлена dual-миграцией для prod и demo.

## 9. Замечания по реализации

- Поскольку у сущности добавляются поля, список, форма и экспорт, при реализации нужно синхронизировать контракт импорта/экспорта с каталогом полей backend.
- Механизм уведомлений следует максимально переиспользовать по аналогии с `backend/domainExpiration.js`.
- Для проекций связей лучше использовать ту же технику и именование trigger-функций, что уже применено в реестре доменов и веб-ресурсов.
