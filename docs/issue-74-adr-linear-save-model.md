# Двухконтурная статусная модель функций и единая линейная модель сохранения ADR

GitHub: https://github.com/dgabadulin/ArchRep/issues/74

> Относится к: интеграции платного модуля **DrawIO Pro** (см. спецификацию модуля в `C:\Users\gabadulindi\isar-diagram-editor\docs`).

---

## 1. Контекст

Для системы и потоков в ядре уже существуют **два независимых контура статусов**:

| Сущность | Статус в реестре (ИТ-ландшафт) | Статус в рамках заключения |
|----------|--------------------------------|-----------------------------|
| Система   | `ar_system_statuses` | `ar_adr_increment_system_statuses` |
| Поток     | `ar_integration_flow_statuses` | `ar_adr_increment_relation_statuses` |

Для **функций** такой двухконтурной модели нет: `ar_system_functions` не имеет ни статуса в реестре, ни статуса в заключении.

Кроме того, сейчас поведение **нелинейное и разное для разных сущностей** при ручном заполнении:

| Сущность | Что происходит сейчас | В чём нелинейность |
|----------|------------------------|--------------------|
| Система   | «+ Новая система» сразу `POST /api/add-ar-systems` (система появляется в реестре) | создаётся раньше, чем нужно |
| Функция   | «Создать» в Dual Listbox — сразу в `ar_system_functions` | как система |
| Поток     | Создаётся только при утверждении (`createFlowsFromConclusion`) | наоборот — позже, чем полезно |

Цель этой задачи — привести все три сущности к **единой линейной модели**: изолированная работа (без записи в БД) → сохранение (одной транзакцией создаются записи в реестрах со «планируемым» статусом) → утверждение (меняются статусы по маппингу).

## 2. Целевая модель

### 2.1. Принципы

1. **Редактор (и DrawIO Pro, и ручная форма) работает изолированно**: до нажатия «Сохранить» в реестры ничего не записывается. Всё хранится в памяти (массивы модуля / данные формы + mxfile диаграммы).
2. **«Сохранить» = одна транзакция**: создаются записи в реестре (`ar_systems`, `ar_system_functions`, `ar_integration_flows`) со статусом «Планируется…» и заполняются связи `ar_adr_increment_*` со статусом «Создается».
3. **Утверждение заключения** (смена на статус из `ADR_APPROVED_STATUS_CODES`) меняет статусы в реестрах **по маппингам** (`ADR_SYSTEM_STATUS_MAP`, `ADR_SYSFUNC_STATUS_MAP`, `ADR_FLOW_STATUS_MAP`).
4. **Существующие данные не меняются** (обратная совместимость: уже созданные системы/функции/потоки остаются как есть).

### 2.2. Маппинг статусов

| Параметр | Назначение | Формат |
|----------|-----------|--------|
| `ADR_SYSTEM_STATUS_MAP` | код статуса системы в заключении → код статуса в реестре | JSON `{incr_code: registry_code}` |
| `ADR_SYSFUNC_STATUS_MAP` | код статуса функции в заключении → код статуса в реестре | JSON `{incr_code: registry_code}` |
| `ADR_FLOW_STATUS_MAP` (уже есть) | код статуса связи → код статуса потока | JSON `{incr_code: registry_code}` |
| `ADR_FLOW_DEFAULT_STATUS_CODE` | статус потока, если статус связи не описан в `ADR_FLOW_STATUS_MAP` | string (код `ar_integration_flow_statuses.code`) |
| `ADR_STATUS_MAP_STRICT` | строгий режим: `false` — не найденный в маппинге статус заменяется статусом по умолчанию (в консоль пишется предупреждение `[refCodes] …`), `true` — статус реестра не меняется | boolean |

Статусы контура заключения, применявшиеся в коде строками, тоже вынесены в параметры (issue #91):

| Параметр | Назначение | Дефолт |
|----------|-----------|--------|
| `ADR_INCR_SYS_NEW_STATUS_CODE` | статус «в решении» для новой системы (`kind:"new"`) | `ADR_INCR_SYS_CREATING` |
| `ADR_INCR_SYSFUNC_NEW_STATUS_CODE` | статус «в решении» для новой функции системы | `ADR_INCR_SYSFUNC_CREATING` |
| `ADR_INCR_SYS_DEFAULT_STATUS_CODE` | статус по умолчанию для системы, уже существующей в реестре (пикер на форме) | `ADR_INCR_SYS_IN_USE` |
| `ADR_INCR_REL_NEW_STATUS_CODE` | статус новой связи решения | `ADR_INCR_REL_CREATING` |
| `ADR_INCR_REL_EXISTING_STATUS_CODE` | статус связи с существующим потоком реестра | `ADR_INCR_REL_IN_USE` |
| `ADR_EDITABLE_STATUS_CODES` | JSON-массив кодов статусов заключения, при которых форма правит состав | `["ADR_STATUS_DRAFT"]` |

Пример наполнения `ADR_SYSTEM_STATUS_MAP`:

```json
{
  "ADR_INCR_SYS_CREATING": "SYS_STATUS_PLANNED",
  "ADR_INCR_SYS_DECOMMISSIONING": "SYS_STATUS_PLANNED_RETIRE"
}
```

Соответствие «действие в решении → статус в реестре» (целевое):

| Действие в заключении | Код | Статус в реестре |
|------------------------|-----|------------------|
| Создается | `ADR_INCR_SYS_CREATING` | «Планируется к внедрению» |
| Используется | `ADR_INCR_SYS_IN_USE` | без изменений (система уже есть) |
| Модифицируется | `ADR_INCR_SYS_MODIFYING` | без изменений (или по согласованию) |
| Выводится | `ADR_INCR_SYS_DECOMMISSIONING` | «Планируется к выводу из эксплуатации» |

## 3. Модель данных

### 3.1. Справочник статусов функций в реестре

```sql
CREATE TABLE archrep.ar_system_function_statuses (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  code varchar NOT NULL UNIQUE,
  name text NOT NULL,
  description text
);
COMMENT ON TABLE archrep.ar_system_function_statuses IS 'Статус функции в ИТ-ландшафте';
```

Начальные строки (рекомендация, финализируется при реализации):

| code | name | description |
|------|------|-------------|
| `SYSFUNC_STATUS_PLANNED` | Планируется | Функция предложена, но не утверждена |
| `SYSFUNC_STATUS_ACTIVE` | Действует | Функция актуальна |
| `SYSFUNC_STATUS_RETIRED` | Выведена | Функция более не используется |

### 3.2. Колонка статуса функции в реестре

```sql
ALTER TABLE archrep.ar_system_functions
  ADD COLUMN ar_system_function_statuses_id bigint
    REFERENCES archrep.ar_system_function_statuses(id);
```

### 3.3. Справочник статусов функций в заключении

```sql
CREATE TABLE archrep.ar_adr_increment_system_function_statuses (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  code varchar NOT NULL UNIQUE,
  name text NOT NULL,
  description text
);
COMMENT ON TABLE archrep.ar_adr_increment_system_function_statuses
  IS 'Статус функции в рамках решения';
```

Начальные строки:

| code | name | Принцип |
|------|------|---------|
| `ADR_INCR_SYSFUNC_CREATING` | Создается | Функция создаётся в рамках решения |
| `ADR_INCR_SYSFUNC_MODIFYING` | Модифицируется | Функция дорабатывается |
| `ADR_INCR_SYSFUNC_IN_USE` | Используется | Существующая функция используется |
| `ADR_INCR_SYSFUNC_DECOMMISSIONING` | Выводится | Функция выводится из эксплуатации |

### 3.4. Колонка статуса функции в заключении

```sql
ALTER TABLE archrep.ar_adr_increment_system_functions
  ADD COLUMN ar_adr_increment_system_function_statuses_id bigint
    REFERENCES archrep.ar_adr_increment_system_function_statuses(id);
### 3.5. Коды статусов систем (для маппинга)

У `ar_system_statuses` сейчас **нет** колонки `code`. Для `ADR_SYSTEM_STATUS_MAP` ввести стабильные коды:

```sql
ALTER TABLE archrep.ar_system_statuses ADD COLUMN code varchar;
-- backfill существующих строк, например:
--   id=2  -> SYS_STATUS_PLANNED        (Планируется к внедрению)
--   id=3  -> SYS_STATUS_IMPLEMENTING   (В процессе внедрения)
--   id=5  -> SYS_STATUS_PRODUCTION     (В промышленной эксплуатации)
--   и т.п.
ALTER TABLE archrep.ar_system_statuses ADD CONSTRAINT ar_system_statuses_code_uniq UNIQUE (code);
```

## 4. API

### 4.1. `POST /api/decisions/applied/full` / `PUT /api/decisions/applied/:id/full`

Расширение входного контракта (обратная совместимость сохраняется):

```jsonc
{
  "task_name": "...",
  "ar_adr_statuses_id": 1,
  "increments": [
    {
      "name": "Решение 1",
      "order_index": 1,
      "systems": [
        {
          "kind": "new",                 // НОВОЕ: "new" | (существующая система по id)
          "code": "SYS-1",
          "name": "Новая система",
          "increment_status_code": "ADR_INCR_SYS_CREATING",
          "functions": [                 // НОВОЕ: функции системы
            { "kind": "new", "name": "Ф-я 1",
              "increment_sysfunc_status_code": "ADR_INCR_SYSFUNC_CREATING" }
          ]
        }
      ],
      "relations": [
        { "kind": "new", "from_ar_systems_id": 123, "to_ar_systems_id": 456,
          "name": "Поток", "increment_relation_status_code": "ADR_INCR_REL_CREATING" }
      ]
    }
  ]
}
```

### 4.2. Логика транзакции в `full`-эндпоинтах

- `systems[]` с `kind:"new"` → INSERT в `ar_systems` с маппингом `ADR_SYSTEM_STATUS_MAP[increment_status_code]`; затем INSERT в `ar_adr_increment_systems` с статусом «Создается».
- `functions[]` (`kind:"new"`) → INSERT в `ar_system_functions` с `ADR_SYSFUNC_STATUS_MAP[...]`; затем INSERT в `ar_adr_increment_system_functions` со статусом в рамках заключения.
- `relations[]` → INSERT в `ar_adr_increment_relations`; поток в реестре (`ar_integration_flows`) создаётся **здесь же** со статусом по `ADR_FLOW_STATUS_MAP[...]` (**не** откладывается до утверждения). Это относится и к связям, добавленным вручную на форме заключения, и к `kind:"new"` из модуля.
- **Идемпотентность потоков (вариант п.3):** связи инкремента при сохранении пересоздаются (новые `id`), поэтому поток привязывается к **заключению** (`ar_adrs_applied_id`) и сопоставляется по **(источник, приёмник, наименование)**; при повторном сохранении он **обновляется** (статус + ссылка на актуальную связь), а не вставляется заново. Тот же апсерт (`syncFlowFromRelation`) используется при утверждении (`createFlowsFromConclusion`) — дублей не возникает.
- **Транзакция:** оба `full`-эндпоинта (`POST` и `PUT`) выполняются в одной транзакции — `BEGIN` после `pool.connect()`, `COMMIT` перед ответом, `ROLLBACK` при ошибке и на ранних выходах (`404`); соединение освобождается в обработчиках. Это критично для `POST`, который теперь получает решения прямо из формы: при сбое на середине (например, на создании связи) не остаётся «полу-созданное» заключение с частью решений.

### 4.3. Смена статуса заключения → применение маппингов

В `PUT /api/decisions/applied/:id/full`, при переходе на статус из `ADR_APPROVED_STATUS_CODES`:

- Найти записи заключения (`заключение → ar_adr_increments → ar_adr_increment_systems/_relations/_system_functions`).
- Для каждой записи применить `ADR_SYSTEM_STATUS_MAP` / `ADR_SYSFUNC_STATUS_MAP` / `ADR_FLOW_STATUS_MAP` к соответствующей записи реестра.
- Не менять уже созданные/существующие записи, у которых статус вне «планируемой» зоны.

## 5. UI (ручная форма)

### 5.1. «+ Новая система» на форме заключения

- Сейчас: `goToNewSystem` → `SystemForm` → сразу `createSystem` в реестр.
- Целевое: `SystemForm` вызывается как **черновик** в контексте заключения — в реестр пишется только при сохранении заключения (`kind:"new"` в `full`).

### 5.2. Функции — единая модалка (Dual Listbox)

- Единый компонент `IncrementSystemFunctionsModal` используется и для систем из реестра, и для новых (черновых) систем строки инкремента.
- Левый список «Функции системы» — **каталог** функций системы из реестра (`ar_system_functions`); для новой системы он пуст.
- Правый список «Функции в решении» — выбранные функции + **статус в рамках заключения**; порядок задаётся drag-and-drop.
- «Создать» создаёт функцию «в памяти» и **сразу помещает её в правый список** (в решение). В реестр функция попадает только при сохранении заключения (`functions[]`, `kind:"new"`, маппинг `ADR_SYSFUNC_STATUS_MAP`).
- Сохранение модалки требует **статус у каждой функции** в правом списке (иначе ошибка, модалка не закрывается).
- Выбор функций строк хранится **в памяти формы** (`systemFunctionsMap`) и уходит в `full` при сохранении заключения; удаление функций из **каталога реестра** из этой модалки не выполняется.
- Поле `ar_adr_increment_systems.comment` — денормализованное зеркало функций (`-Имя;\r\n`), именно его рисует тело узла на схеме решения (`incrementDiagram.js`). `full`-эндпоинты (`POST` и `PUT`) **пересчитывают** `comment` из актуального `functions[]`; присланный `comment` используется только как fallback, когда массив функций не передан (обратная совместимость). Это устраняет случай, когда после добавления функции схема показывала старый список.

### 5.3. Интеграции (связи) в ручной форме

- Модалка «Интеграции в решении» (`IncrementRelationsModal`): сверху пара «Система-источник → Система-получатель» с подсказкой, что указывается направление **передачи данных**, а не направление инициирующего вызова.
- Левая панель — **«Существующие потоки данных»** (потоки реестра по выбранной паре; одиночный выбор, направление учитывается; уже выбранные в решении исключаются). Для новых (черновых) систем потоков в реестре нет — доступно только «Создать». Если по паре нет свободных потоков: «В реестре отсутствуют потоки данных по заданным условиям — используйте кнопку «Создать»».
- Правая панель — **«Интеграции в решении»** (связи, отфильтрованные по выбранной паре); в строке выводятся только передаваемые данные и статус. Пустых состояний и счётчиков не выводится (список просто пустой либо содержит связи этой пары).
- Кнопки между списками (`>> В решение`, `<< Убрать`, «Создать») **неактивны, пока не заданы оба верхних поля** (источник и получатель; при совпадении — тоже неактивны).
- Кнопки: `>> В решение` (перенос существующего потока — форма предзаполняется, статус по умолчанию «Используется»), `<< Убрать`, «Создать» (новая связь, статус по умолчанию «Создается»).
- Компактная форма (аналог формы реестра): источник, получатель, тип инициирующего события, периодичность, передаваемые данные, способ передачи + **статус связи в заключении**. Для выбранного потока — пометка с его `id` и текущим статусом в реестре.
- Валидации: источник ≠ получатель; для статусов «Используется / Модифицируется / Удаляется» обязателен выбранный поток реестра.
- Связь хранит ссылку на поток (`ar_integration_flows_id`) и реестровые поля (`transferred_data`, `transfer_method`, `periodicity`, `ar_integration_flow_event_types_id`); legacy-колонки `name` / `description` — зеркало реестровых полей (совместимость).
- Сохранение заключения (`full`): выбранный существующий поток **обновляется** (статус по `ADR_FLOW_STATUS_MAP`; реестровые поля — при «Модифицируется»), новый поток создаётся; ссылка дозаполняется в связи. «Удаляется» → статус потока `FLOW_STATUS_4` («Исключена»).
- В таблице блока «Интеграции» на форме заключения у строки есть только **«Удалить»**: изменение связи выполняется в модалке (правая панель → «Изменить» у строки). Ссылка «Изменить» из таблицы убрана как дублирующая (она открывала модалку без передачи строки).
- До сохранения заключения черновые системы/связи не видны в «Схемах» — диаграммы строятся из БД, поэтому при несохранённых изменениях перед формированием схемы показывается модалка «Сохранить и продолжить» (см. 5.5).

### 5.4. Системы в решении (существующие из реестра)

- Добавление системы из каталога в решение — **локальное** (`addSystem`), без `POST /api/increments/:id/systems`; строка получает `_local: true` и ключ `_localRowId` (`lr:<n>`).
- Удаление системы из решения — тоже **локальное** (без `DELETE`): строка убирается из списка, её ещё не сохранённые интеграции удаляются вместе с ней (с подтверждением).
- Функции таких строк доступны сразу: каталог берётся из реестра (`GET /api/ar-systems/:id/system-functions`), выбор хранится в памяти.
- В таблице систем такая строка помечается бейджем «не сохранено».
- Всё уходит в БД одной транзакцией при сохранении заключения (`full`): строки `ar_adr_increment_systems` + `functions[]`.

### 5.5. Схемы решения: сохранение перед формированием (A1)

Схема строится по **сохранённым** данным (`buildMxfile` на сервере: инкремент + системы + связи из БД), поэтому:

- Кнопка «Создать схему решения» и ссылка «Обновить» в таблице схем не блокируются при несохранённых изменениях, а также когда заключение ещё не сохранено (id нет): клик открывает модалку сохранения.
- Если форма «грязная» (`isDirty` по полям заключения **или** `structureDirty` по системам/функциям/интеграциям), клик открывает модалку **«Перед формированием схемы решения необходимо сохранить внесенные изменения»** с кнопками **«Сохранить и продолжить»** и **«Отмена»**.
- «Сохранить и продолжить»: `submit({ skipNavigate: true })` (заключение сохраняется, пользователь остаётся на форме), затем выполняется отложенное действие (`pendingDiagramAction`): создание схемы или merge существующей.
- Если заключение ещё **не сохранено** (нет id): кнопка всё равно доступна, модалка предлагает сохранить; после `POST /full` форма переходит на `/:id/edit`, данные перечитываются из БД и отложенное действие выполняется уже там.
- Ошибка сохранения — модалка остаётся открытой, текст ошибки внутри неё; действие не выполняется.
- «Отмена» — модалка закрывается, никаких записей не делается.
- После сохранения строки инкрементов пересоздаются, поэтому формы перечитывают данные (`reloadAfterSave`: `increments`, системы, связи, функции), а схема для «Обновить» ищется по `id`, затем по `version_no`.
- `useUnsavedGuard` учитывает и поля, и структуру (`formHasUnsavedChanges`) — структурные правки больше не теряются при уходе со страницы.

Сохранность самих схем: `ar_adr_increment_diagrams.ar_adr_increment_id` → `ON DELETE CASCADE`, а `PUT full` (черновик) пересоздаёт строки инкрементов. Поэтому перед удалением инкрементов схемы читаются (`adr_increment_diagrams_by_applied`), а после пересоздания возвращаются (`adr_increment_diagrams_insert_full`) с сопоставлением по `(order_index, наименование решения)` — версии, `mxfile`, автор и таймстемпы сохраняются.

### 5.6. Регрессия

- Старые заключения и существующие системы/функции/потоки не меняем.
- `PUT full` без `increments` продолжает работать как «только статус».

### 5.7. Решения (инкременты): локальная модель при создании заключения

- На форме **нового** заключения (`/decisions/applied/new`) ввод решений больше не блокируется: решения копятся **в памяти** (`_local: true`, локальный ключ `linc:<n>`), как системы/функции/интеграции.
- Живые запросы к БД для локальных решений не выполняются: `loadIncrementSystems`, `loadIncrementRelations`, `loadIncrementDiagrams` для `linc:`-ключей выходят сразу (данные уже в памяти). Кнопка «Создать схему решения» при этом доступна и до сохранения: клик открывает модалку сохранения (см. 5.5).
- Сохранение нового заключения — **одна операция**: `POST /api/decisions/applied/full` с собранным `increments[]` (общая функция `buildIncrementsPayload()` используется и для `POST`, и для `PUT`). Запись ADRA создаётся первой, затем решения, системы (в т.ч. `kind:"new"`), функции, связи и потоки — как и в режиме редактирования.
- После успешного `POST` форма переходит на `/decisions/applied/:id/edit`, данные перечитываются из БД; локальные (временные) ключи больше не используются.
- Локальное решение можно изменить и удалить: изменения — в памяти, удаление каскадно убирает его системы, черновые системы и интеграции (тоже в памяти). Строка помечается бейджем «не сохранено».
- Все несохранённые изменения (в т.ч. добавленные решения) отслеживаются `formHasUnsavedChanges` — сторож ухода со страницы предупредит до потери данных.
- Маршруты `/decisions/applied/new` и `/decisions/applied/:id/edit` используют **один и тот же компонент**, поэтому при переходе после сохранения `onMounted` не вызывается: данные из БД читаются явно (`reloadAfterSave()`), иначе блоки решений/систем/интеграций остаются пустыми.

## 7. Критерии готовности ядра

- [ ] Миграция (`DB/scripts/*.sql` + `DB/migrations/*.js`): справочники функций, колонки, коды систем.
- [ ] `refCodes` резолвит коды `ar_system_statuses`, `ar_system_function_statuses`.
- [ ] Параметры `ADR_SYSTEM_STATUS_MAP`, `ADR_SYSFUNC_STATUS_MAP` применяются при создании и при утверждении.
- [ ] `refCodes` резолвит коды `ar_system_statuses`, `ar_system_function_statuses`, `ar_integration_flow_statuses`; расхождение маппинга и справочника пишет предупреждение `[refCodes] …` (и не меняет статус при `ADR_STATUS_MAP_STRICT=true`).
- [ ] Статусы контура (новая система/функция, новая и существующая связь, статус по умолчанию в пикере) и список редактируемых статусов заключения — параметры `ADR_INCR_*` / `ADR_EDITABLE_STATUS_CODES`, а не строки в коде формы и эндпоинтов.
- [ ] `full`-эндпоинты создают системы/функции/потоки одной транзакцией со статусами планирования.
- [ ] Потоки создаются/обновляются идемпотентно по `(заключение, источник, приёмник, наименование)` — повторное сохранение не плодит дубли.
- [ ] При смене на статус из `ADR_APPROVED_STATUS_CODES` статусы в реестрах меняются по маппингам.
- [ ] Ручная форма: новая система/функция не пишется в реестр до сохранения заключения.
- [ ] Ручная форма: интеграции — черновик в памяти; в списках «источник/приёмник» доступны новые системы заключения; при сохранении связи создаются с реальными id.
- [ ] Интеграции: можно использовать/модифицировать существующий поток реестра (ссылка `ar_integration_flows_id`); повторное сохранение не плодит дубли; «Модифицируется» обновляет реестровые поля потока.
- [ ] Ручная форма: добавление/удаление существующих систем в решение — локально, без немедленных POST/DELETE.
- [ ] Схемы: при несохранённых изменениях «Создать схему решения»/«Обновить» показывают модалку с «Сохранить и продолжить»/«Отмена»; после сохранения действие выполняется автоматически.
- [ ] Схемы не удаляются при пересохранении черновика заключения (восстановление после пересоздания инкрементов).
- [ ] Новое заключение: решения можно добавлять/изменять/удалять до сохранения (в памяти), затем одно `POST /full` создаёт запись вместе с решениями, системами, функциями и связями.
- [ ] Оба `full`-эндпоинта выполняются в транзакции: при ошибке не остаётся частично созданных данных.
- [ ] Dual Listbox показывает статус функции в заключении; «Создать» добавляет функцию сразу в решение, при сохранении модалки статус обязателен.
- [ ] Регрессия существующих заключений/систем без изменений.
