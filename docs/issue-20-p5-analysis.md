# Задача #20, п.5: анализ с учётом маппинга полей и справочников статусов

## 1. Маппинг полей при создании записей в реестре интеграций

При переводе архитектурного заключения из статуса **Черновик** в **Утверждено архитектором** или **Утверждено арх.советом** для каждой записи из `ar_adr_increment_relations` (по всем инкрементам заключения) создаётся запись в `ar_integration_flows`:

| Поле в ar_adr_increment_relations | Поле в ar_integration_flows | Примечание |
|-----------------------------------|-----------------------------|------------|
| from_ar_systems_id                | source_ar_systems_id        | напрямую   |
| to_ar_systems_id                  | target_ar_systems_id        | напрямую   |
| **name**                          | **transferred_data**        | по согласованию |
| **description**                   | **transfer_method**         | по согласованию |
| ar_integration_flow_event_types_id| —                           | при создании из заключения: NULL или дефолт (по событию/по расписанию) |
| ar_adr_increment_relation_statuses_id | ar_integration_flow_statuses_id | маппинг по справочникам (см. ниже) |

## 2. Справочники статусов (из сидов в репозитории)

### 2.1 ar_integration_flow_statuses (реестр интеграций)

Из `DB/schema/archrep_integration_flows.sql` и `archrep_integration_flows_seed.sql`:

| id (примерно) | name                         | description |
|---------------|------------------------------|-------------|
| 1             | планируется к реализации     | NULL        |
| 2             | в процессе реализации        | NULL        |
| 3             | в промышленной эксплуатации  | NULL        |
| 4             | исключена                    | NULL        |
| 5             | реализация отменена          | NULL        |

### 2.2 ar_adr_increment_relation_statuses (статус интеграции в инкременте)

Фактические значения из справочника (temp / экран):

| id | name           | description                    |
|----|----------------|--------------------------------|
| 1  | Создается      | Интеграционный по...           |
| 2  | Модифицируется | Дорабатывается сущ...         |
| 3  | Используется   | В рамках решения и...          |
| 4  | Удаляется      | Интеграционный по...           |

Смысл: действие над интеграцией в рамках заключения (создать, изменить, использовать, удалить), а не этап жизненного цикла.

| id | name                            | description        |
|----|---------------------------------|--------------------|
| 1  | Планируется к реализации        | Интеграционный по...|

| 3  | В промышленной эксплуатации     | Интеграционный по...|
| 4  | Исключена                       | Ранее реализованны...|
| 5  | Реализация отменена             | Предложенный к ре...|

## 3. Маппинг статусов: adr_relation_status → integration_flow_status

По смыслу «действие в заключении» → «этап в реестре»:

| ar_adr_increment_relation_statuses (name) | → ar_integration_flow_statuses (id / name)      |
|------------------------------------------|--------------------------------------------------|
| Создается                                | 1 — Планируется к реализации                     |
| Модифицируется                           | 3 — В промышленной эксплуатации                  |
| Используется                             | 3 — В промышленной эксплуатации                  |
| Удаляется                                | 4 — Исключена (или 5 — Реализация отменена) *   |
| NULL / неизвестный                       | 1 — Планируется к реализации (дефолт)            |

\* Для «Удаляется» можно выбрать «Исключена» (id 4) как «уже была, снята с эксплуатации» или «Реализация отменена» (id 5) как «реализацию отменили». Рекомендация: **Исключена** (id 4), если в описании статуса речь о ранее реализованных; иначе — id 5.

Реализация на бэкенде: по `ar_adr_increment_relation_statuses_id` взять name из `ar_adr_increment_relation_statuses`, по таблице маппинга выше определить id в `ar_integration_flow_statuses`, подставить в `ar_integration_flow_statuses_id`. При NULL или неизвестном name — подставлять id = 1.

Если в файлах **temp/integrationFlowStatuses.xlsx** и **temp/adrRelationStatuses.xlsx** состав или названия статусов отличаются от сидов, маппинг нужно дополнить. Для выгрузки содержимого xlsx в JSON из корня проекта:  
`node temp/read-statuses.js`

## 4. Связь заключение и связь (relation) — интеграционный поток

- В **ar_integration_flows** добавить столбцы:
  - **ar_adrs_applied_id** (int8 NULL, FK на archrep.ar_adrs_applied(id)) — из какого заключения создана запись;
  - **ar_adr_increment_relation_id** (int8 NULL, FK на archrep.ar_adr_increment_relations(id)) — из какой связи инкремента создана запись.
- При создании записи в реестре из утверждённого заключения заполнять оба поля.
- При повторном утверждении (п.6): не создавать запись в `ar_integration_flows` для связи, по которой поток уже создан. Критерий: **уже есть поток с ar_adr_increment_relation_id = id данной связи** — тогда пропустить. Таким образом, одна связь (relation) даёт не более одной записи в реестре; в одном заключении несколько связей с одинаковыми source/target дают несколько записей в реестре — это допустимо.

## 5. Итоговая логика при смене статуса на «утверждён»

1. Проверить: новый статус = «Утверждено архитектором» или «Утверждено арх.советом».
2. Для каждого инкремента заключения (ar_adr_increments WHERE ar_adrs_applied_id = :id) взять все ar_adr_increment_relations.
3. Для каждой связи (ar_adr_increment_relations):
   - Если уже существует запись в ar_integration_flows с ar_adr_increment_relation_id = id этой связи — пропустить (поток по этой связи уже создан).
   - Иначе вставить в ar_integration_flows:
     - source_ar_systems_id := from_ar_systems_id
     - target_ar_systems_id := to_ar_systems_id
     - transferred_data := name (из relation)
     - transfer_method := description (из relation)
     - ar_integration_flow_event_types_id := NULL (или дефолт)
     - ar_integration_flow_statuses_id := по маппингу из ar_adr_increment_relation_statuses (по имени → id в ar_integration_flow_statuses)
     - ar_adrs_applied_id := id заключения
     - ar_adr_increment_relation_id := id данной связи (ar_adr_increment_relations.id)
4. Обновить ar_adrs_applied.ar_adr_statuses_id на новый статус.

---

## 6. Связь заключение — система

Без изменений DDL: связь «заключение — система» считается через цепочку заключение → инкременты → ar_adr_increment_systems → системы. Отдельную таблицу ar_adrs_applied_systems не вводим, пока не понадобится явная связь на уровне заключения или отдельные типы связи.
