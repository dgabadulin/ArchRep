# Как работает `node-pg-migrate` (в контексте этого репозитория)

`node-pg-migrate` — это **CLI и библиотека** для PostgreSQL: подключается к БД, смотрит **какие миграции уже применены**, и по очереди выполняет **ещё не применённые** файлы из каталога миграций.

Краткая справка по репо: `DB/README.md` (раздел «Миграции»), скрипты в `package.json`, деплой в `infra/demo/DEPLOYMENT.md`.

**Договорённость репозитория:** любое новое изменение БД, которое должно жить и на проде, и на демо, сопровождается **двумя** файлами: **`DB/scripts/*.sql`** (прод, `psql`) и **`DB/migrations/*.js`** (демо, эта цепочка). Содержание по эффекту согласовано.

---

## 1. Конфигурация и подключение к БД

При запуске (например `npm run db:migrate`) используется **`pgmrc.json`** (в скриптах явно: `--config-file pgmrc.json`). Имя с расширением `.json` нужно для **Node 20 + ESM**: `node-pg-migrate` v8 подгружает конфиг через `import()` с assertion `type: 'json'`, без `.json` Node выдаёт `ERR_IMPORT_ASSERTION_TYPE_FAILED`.

В проекте задано в том числе:

| Параметр | Значение в `pgmrc.json` | Смысл |
|----------|---------------------|--------|
| `databaseUrl` | `env:DATABASE_URL` | Строка подключения берётся из переменной окружения **`DATABASE_URL`** (формат `postgres://user:pass@host:port/dbname`). |
| `dir` | `DB/migrations` | Каталог миграций (дублируется флагом CLI `--migrations-dir DB/migrations`). |
| `migrationsTable` | `pgmigrations` | Таблица учёта применённых миграций. |
| `migrationsSchema` | `public` | Схема для этой таблицы. |
| `checkOrder` | `true` | Строгая проверка порядка (см. ниже). |

Без корректного **`DATABASE_URL`** подключение завершится ошибкой.

---

## 2. Каталог миграций и порядок

Файлы лежат в **`DB/migrations/`**, имя обычно вида:

`YYYYMMDDHHMMSS_описание.js`

Пример в репозитории: `20260424120000_add_tech_radar_embed_url_param.js`.

**Порядок выполнения** — по **имени файла** (префикс с датой/временем задаёт линейную последовательность).

---

## 3. Формат одной миграции

Каждый файл — Node-модуль с экспортами:

- **`exports.up(pgm)`** — действия при **накате** (вперёд);
- **`exports.down(pgm)`** — действия при **откате** (назад).

Объект **`pgm`** — builder API: `pgm.sql('…')`, `pgm.createTable`, `pgm.addColumn` и т.д. Операции выполняются инструментом против БД (часто миграция выполняется в **транзакции** — зависит от версии и настроек; по умолчанию для `up` обычно ожидают атомарность на уровне одной миграции).

Пример из репозитория: в `up` — `INSERT … ON CONFLICT DO NOTHING`, в `down` — соответствующий `DELETE` по `code`.

---

## 4. Таблица учёта `public.pgmigrations`

При первом успешном запуске инструмент **создаёт** таблицу (если её ещё нет) и записывает туда **идентификаторы применённых** миграций.

Пока запись для файла есть в `pgmigrations`, **`up` для этого файла снова не выполняется** — это основа идемпотентности команды «накатить всё недостающее».

---

## 5. Команда `up` (`npm run db:migrate`)

Логика **`node-pg-migrate up`** (упрощённо):

1. Подключиться к БД по `DATABASE_URL`.
2. Убедиться, что существует таблица `pgmigrations` (создать при необходимости).
3. Прочитать список файлов в `DB/migrations`, отсортировать по имени.
4. Сравнить с записями в `pgmigrations`.
5. Для каждого файла, **которого ещё нет** в таблице:
   - загрузить модуль;
   - выполнить **`up(pgm)`**;
   - при успехе — **записать** миграцию в `pgmigrations`.
6. Если новых миграций нет — завершиться без изменений схемы.

С **`checkOrder: true`**: если в БД уже применены миграции с большим таймстемпом, а в репозитории появился файл с **меньшим** таймстемпом («вставили миграцию в середину истории»), выполнение **завершится ошибкой**, чтобы не ломать согласованность истории.

---

## 6. Команда `down` (`npm run db:migrate:down`)

Откатывает применённые миграции (обычно **последнюю** или пачку — уточняйте флаги в документации версии **^8** для точного поведения по умолчанию): вызывается **`down(pgm)`**, затем запись **удаляется** из `pgmigrations`.

---

## 7. Создание новой миграции (`npm run db:migrate:create`)

Генерирует новый файл в `DB/migrations/` с текущим таймстемпом; дальше вручную дописываются `up` / `down`.

---

## Связка с демо-деплоем

В сценариях **full** и **api-only** (`infra/demo/remote_demo_deploy.sh`) перед запуском API вызывается **`npm run db:migrate`**: к уже существующей схеме/дампу донажимаются только те JS-миграции, которых ещё нет в `pgmigrations`.

---

## Полезные команды (из `package.json`)

```bash
npm run db:migrate          # node-pg-migrate up
npm run db:migrate:down     # откат (осторожно в shared БД)
npm run db:migrate:create   # шаблон нового файла
```
