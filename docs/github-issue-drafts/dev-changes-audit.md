## Цель

Реализовать в ядре ИСАР **аудит изменений**: журнал «кто, когда и что изменил» по реестровым сущностям, архитектурным заключениям и служебным операциям — с просмотром истории на формах и отдельным экраном.

## Контекст (зачем)

1. Сейчас история есть только у запусков заданий (`ar_job_runs`) и частично у ADR (`ar_adrs_applied.updated_at`). По реестрам (ИС, функции, потоки, домены, сертификаты и т.д.) истории изменений нет.
2. Находка при разборе issue #74: перевод архитектурного заключения из «Утверждено…» обратно в «Черновик» **не откатывает** статусы в реестрах (`ar_systems`, `ar_system_functions`, `ar_integration_flows`), и прежнее значение взять негде: у `ar_systems` нет даже `updated_at`, истории статусов нет. Ответить на вопрос «кто и когда изменил статус системы» невозможно.
3. Для корпоративного контура нужен след изменений: разбор инцидентов, подтверждение «мы ничего не меняли», контроль массовых операций (импорт, пересборка проекций, сервисные операции, утверждение ADR).

## Предлагаемый scope (MVP)

1. **Таблица журнала** (dual-миграция: `DB/scripts/*.sql` + `DB/migrations/*.js`): `archrep.ar_change_log`
   - `id`, `changed_at timestamptz NOT NULL DEFAULT now()`,
   - `changed_by_user_id` (FK `ar_app_users`, NULL для системных операций),
   - `entity_type` (код сущности: `system`, `system_function`, `integration_flow`, `adr_applied`, `domain`, `certificate`, …),
   - `entity_id`, `entity_code` (человекочитаемо),
   - `action` (`insert` / `update` / `delete`),
   - `source` (`ui` / `import` / `job` / `adr` / `service_operation` / `api`),
   - `changes jsonb`: `{ "<field>": { "from": …, "to": … } }` — только изменённые поля,
   - `context jsonb` (напр. `{ adr_code, job_code, import_batch }`), `request_id`.
   - Индексы: `(changed_at DESC)`, `(entity_type, entity_id, changed_at DESC)`, `(changed_by_user_id)`.
2. **Способ записи — развилка** (см. открытые вопросы):
   - (A) код в BFF: явный хелпер в обработчиках — есть точный контекст пользователя/источника;
   - (B) Postgres-триггеры `AFTER INSERT/UPDATE/DELETE` — гарантированный охват, но пользователя надо передавать через `SET LOCAL app.user_id` в транзакции.
   Рекомендация: A для реестровых CRUD и ADR-статусов, B — как «страховка» для критичных таблиц.
3. **Просмотр:**
   - блок «История изменений» на карточках реестров и в архитектурных заключениях (кто/когда/поле/было → стало);
   - отдельный экран («Настройки → Аудит изменений» или «Администрирование») со списком и фильтрами: период, пользователь, сущность, действие, источник;
   - экспорт по текущему фильтру.
4. **RBAC:** новые права `audit:read` (по умолчанию только `SYSTEM_ADMIN`) и `audit:export` — `permissionsCatalog.js` (`ALL_PERMISSIONS` + `ROLE_PERMISSIONS`), правила в `routePermissions.js`, `npm run check:routes` зелёный; после добавления — перезапуск API (`bootstrapAuth` синхронизирует права).
5. **Специальный случай (закрывает находку #74):** фиксировать изменения статусов в реестрах по маппингам ADR (`ADR_SYSTEM_STATUS_MAP`, `ADR_SYSFUNC_STATUS_MAP`, `ADR_FLOW_STATUS_MAP`) с указанием заключения в `context`.

## Вне scope (MVP)

- Полное версионирование/event-sourcing сущностей и откат «к версии».
- Аудит чтения данных (только изменения).
- Аудит системных параметров и секретов (отдельная задача при необходимости).
- Хранение полного «до/после» для больших текстовых полей (вариант: хэш + усечённое значение).

## Открытые вопросы

1. Способ записи: триггеры Postgres, код BFF или комбинация? Если триггеры — как передавать пользователя (`SET LOCAL app.user_id` в транзакции, `request_id`)?
2. Охват MVP: только ключевые сущности (ИС, функции, потоки, ADR, домены, сертификаты) или все реестры сразу?
3. Глубина хранения и ретеншен (например, 3 года), лимит на размер `changes` для длинных полей.
4. Нужен ли «откат значения» из журнала и каким правом он закрывается?
5. Массовые операции (импорт, пересборка проекций, сервисные операции, утверждение ADR) — писать агрегированно (одна запись на batch) или по строкам?
6. Где размещать экран: «Настройки» или «Администрирование»; нужен ли экспорт в Excel.

## Критерии готовности

- [ ] Dual-миграция журнала (`DB/scripts/*.sql` + `DB/migrations/*.js`) и сиды прав.
- [ ] Права `audit:read`, `audit:export` в `permissionsCatalog.js` (+ матрица ролей), правила в `routePermissions.js`, `npm run check:routes` зелёный, после перезапуска API права синхронизированы.
- [ ] Изменения фиксируются для выбранных сущностей: insert/update/delete, поля «было → стало», кто/когда/источник.
- [ ] Изменение статуса системы/функции/потока при утверждении ADR попадает в журнал со ссылкой на заключение (`context.adr_code`) — закрывает находку #74.
- [ ] UI: блок «История изменений» на карточке + экран со списком, фильтрами и экспортом; доступ строго по правам.
- [ ] Ручная проверка: изменить карточку ИС, изменить статус, утвердить заключение, выполнить импорт — в журнале корректные записи с пользователем и источником.
