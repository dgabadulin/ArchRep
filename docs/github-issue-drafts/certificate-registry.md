## Контекст

В ИСАР уже реализованы:

- реестр доменов: `docs/domain-registry-schema.md` ([#67](https://github.com/dgabadulin/ArchRep/issues/67));
- Job Runner и уведомления об истекающих доменах: `docs/job-runner-design.md` ([#68](https://github.com/dgabadulin/ArchRep/issues/68));
- механизм FK-проекций в `ar_metamodel_relations` через PostgreSQL trigger, применённый для других реестров.

Нужно добавить реестр сертификатов, связать его с доменами и сотрудниками через проекции, а также включить периодические email-уведомления по срокам окончания сертификатов.

## Цель

Реализовать реестр сертификатов с UI/API/БД, автогенерацией кода, триггерными FK-проекциями в метамодель и периодической проверкой сроков окончания сертификатов через уже существующий механизм Job Runner.

## Требования

### 1. Реестр сертификатов

Создать табличную форму и форму редактирования реестра сертификатов со следующими атрибутами:

- `code` — код сертификата, автогенерация на backend в формате `CRT-<номер по порядку>` без лидирующих нулей;
- `ar_domains_id` — ссылка на реестр доменов, **обязательное** поле;
- `ca_ar_partners_id` — сертификационный центр, ссылка на справочник партнёров;
- `issued_at` — дата выпуска, **обязательное** поле;
- `expires_at` — дата окончания, **обязательное** поле;
- `wildcard_flag` — boolean / checkbox;
- `placement_url` — текстовое поле без обязательной URL-валидации;
- `responsible_ar_employees_id` — ссылка на справочник сотрудников.

Ожидаемое поведение:

- код нельзя вводить руками в UI;
- при создании записи код присваивается автоматически;
- список и форма должны быть оформлены по аналогии с реестром доменов;
- для сущности добавить стандартные права `certificate:read`, `certificate:write`, `certificate:delete`, `certificate:export`.

### 2. Проекции связей в метамодель

Создать relation types и синхронизацию проекций по FK через trigger:

1. `certificate_domain` — связь **«Выпущен для»** между `certificate -> domain`, источник: `ar_certificates.ar_domains_id`;
2. `certificate_employee_responsible` — связь **«Ответственный»** между `certificate -> employee`, источник: `ar_certificates.responsible_ar_employees_id`.

Требования к реализации:

- использовать уже применявшийся механизм trigger-based FK projections;
- при `INSERT/UPDATE` очищать старые проекции для сертификата и создавать актуальные;
- при `DELETE` удалять соответствующие проекции;
- выполнить backfill для уже существующих строк;
- payload в `ar_metamodel_relations` оформлять по аналогии с другими FK-проекциями.

### 3. Уведомления об истечении сертификатов

Используя механизм из [#68](https://github.com/dgabadulin/ArchRep/issues/68), добавить новое периодическое задание:

- код job: `certificate_expiration_check`;
- период запуска: 1 раз в 3 дня (`interval_seconds = 259200`);
- параметры:
  - `CHK_CERT_EXPIRATION` — число дней до окончания, порог уведомления;
  - `CHK_CERT_EXPIRATION_EMAIL` — email получателя(ей), несколько адресов через запятую.

Правила отбора сертификатов:

- логика отбора **как у доменов**:
  - `expires_at IS NOT NULL`;
  - `expires_at >= CURRENT_DATE`;
  - `expires_at <= CURRENT_DATE + CHK_CERT_EXPIRATION`;
- если сертификатов в окне нет — письмо не отправлять, run = `success`;
- если email не задан — письмо не отправлять, но run = `success` с понятным сообщением;
- повторные письма допустимы при каждом успешном цикле, пока запись остаётся в окне проверки.

Состав уведомления:

- домен;
- код сертификата;
- дата окончания;
- ответственный.

Тема и формат письма — по аналогии с уведомлением об истекающих доменах.

## Затрагиваемые области

- `DB/scripts/` и `DB/migrations/` — dual-миграция;
- `backend/queries.js`, CRUD/API реестра;
- backend-модуль проверки сроков сертификатов + handler Job Runner;
- `frontend-v3` — список, форма, роут, меню, экспорт;
- импорт/экспорт Excel для новой сущности, если реестр поддерживает общий контракт экспорта/шаблона.

## Критерии готовности

1. В БД есть таблица реестра сертификатов, все нужные FK, индексы и автогенерация кода `CRT-N`.
2. В UI доступны список и форма редактирования сертификатов.
3. Проекции `certificate -> domain` и `certificate -> employee` синхронизируются триггером при insert/update/delete.
4. В Job Runner зарегистрировано задание `certificate_expiration_check`.
5. В БД созданы параметры `CHK_CERT_EXPIRATION` и `CHK_CERT_EXPIRATION_EMAIL`.
6. Email-уведомление содержит домен, код сертификата, дату окончания и ответственного.
7. Реализация выполнена dual-миграцией: `DB/scripts/...sql` + `DB/migrations/...js`.
