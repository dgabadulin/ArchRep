## Контекст

В ИСАР уже реализованы:

- прикладные permissions в БД;
- роли `ar_roles` и назначения `ar_user_roles`;
- экран ролей в админке;
- редактирование существующей роли и настройка её permissions;
- назначение ролей пользователям на экране пользователей.

Сейчас отсутствует полный CRUD ролей через UI: роль нельзя полноценно создать и безопасно удалить средствами приложения.

## Цель

Обеспечить самостоятельное управление прикладными ролями внутри ИСАР через UI без использования Keycloak Admin API:

- создание новой роли;
- редактирование роли;
- удаление роли;
- сохранение и изменение набора permissions роли.

## Принятые решения

1. Роли живут только внутри ИСАР, без записи в Keycloak.
2. Шаблонные роли пока не требуются.
3. Изменение permissions у роли сразу влияет на всех пользователей, которым она назначена.
4. Soft-delete не используется.
5. Аудит изменений ролей и назначений в эту задачу не входит.

## Ограничения

### Системные роли

Системные роли нельзя удалять. Допустимость их редактирования определяется текущими ограничениями backend и UI.

### Удаление назначенной роли

Если роль назначена хотя бы одному пользователю:

- backend возвращает ошибку бизнес-валидации;
- UI показывает понятное предупреждение;
- в сообщении предлагается сначала снять эту роль у пользователей.

Удаление должно быть разрешено только для роли без назначений.

## Scope реализации

### Backend

- добавить API создания роли;
- добавить API удаления роли;
- добавить валидации:
  - обязательность кода и имени;
  - уникальность кода;
  - запрет удаления системной роли;
  - запрет удаления роли, если она назначена пользователям.

### Frontend

- расширить экран ролей действиями создания и удаления;
- доработать форму роли для режима создания;
- показывать сообщения об ошибке удаления в понятном виде;
- сохранить текущую работу матрицы permissions.

### База данных

Новая схема не требуется, если текущих таблиц `ar_roles`, `ar_role_permissions` и `ar_user_roles` достаточно. При необходимости допускается точечная миграция под ограничения или значения по умолчанию.

## Вне scope

- аудит ролей и назначений;
- синхронизация ролей с Keycloak;
- шаблонные роли;
- массовые операции по ролям;
- отдельный мастер снятия роли у всех пользователей.

## Критерии готовности

1. Администратор с нужными permissions может создать новую роль через UI.
2. Администратор может изменить имя, описание и permissions существующей роли.
3. Администратор может удалить неназначенную несистемную роль.
4. При попытке удалить назначенную роль UI получает и показывает понятное предупреждение.
5. Назначение роли пользователю продолжает работать без регрессий.
