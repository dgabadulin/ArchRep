# Подключение подключаемого модуля: инструкция администратора

> ⚡ **Нужно быстро?** Короткий пошаговый чеклист без теории:
> [`docs/modules-connect-checklist.md`](./modules-connect-checklist.md) — 11 пунктов «файл → папка → env → ключ → проверка».
> Этот документ — полная версия с диагностикой и обоснованиями.

Относится к: `docs/modules-contract.md` (контракт модулей), `modules/README.md` (drop-in каталог).

Аудитория: администратор инсталляции ИСАР (есть доступ к серверу/контейнерам и env, умеет
применять миграции). Разработка модулей **не** входит в инструкцию.

Обозначения: `<code>` — код модуля от поставщика (`drawio-pro`), `<version>` — его версия (`0.1.0`),
`<BASE_URL>` — адрес стенда (`https://isar.example.ru`, `http://10.0.0.5:3000`).

> **Три состояния модуля — не путать:**
> 1. **Установлен** — пакет физически есть в сборке (`@isar/<code>` или `modules/<code>`).
> 2. **Включён** — `ENABLED_MODULES` / `SYS_MODULE_<code>_ENABLED` / `enabled=true` в `isar_modules`.
> 3. **Лицензирован** — в env есть валидный ключ `SYS_MODULE_<code>_LICENSE`.
>
> Модуль работает, только когда включён **и** лицензирован (если лицензия обязательна).
> Установка ≠ включение: поставленный, но не включённый модуль ничего не делает.

---

## 0. Что понадобится

| Что | Зачем | Где взять |
|---|---|---|
| Версия ядра | сверить `requiresCore` | `package.json` → `version` (сейчас `1.0.0`) |
| Пакет модуля (`@isar/<code>` или zip) | код модуля | поставщик модуля / приватный registry |
| Лицензионный ключ | включить платный модуль | поставщик; ключ привязан к `instance_id` |
| Публичный ключ Ed25519 | проверка подписи лицензии | поставщик / настройки ядра |
| Доступ к БД | миграция + реестр `isar_modules` | DBA / сервер |
| Доступ к env и перезапуску API | включение | сервер/контейнер |

**Что НЕ понадобится:** правка кода ядра, правка кода модуля, прямой доступ модуля к таблицам ядра.
Все несовпадения форматов закрываются адаптерами ядра (см. `docs/modules-contract.md` §16.6).

## 1. Проверить совместимость модуля с ядром

Модуль объявляет `requiresCore` (semver-диапазон). Ядро при старте **не запускает** модуль,
если диапазон не выполняется: в лог пишется
`[modules] <code>: requires core <range>, have <версия> — модуль не запущен`.

Проверка до установки — по манифесту из артефакта:

```bash
# module.json (контракт) или manifest.json (legacy — ядро применит адаптер)
type module.json | findstr requiresCore        # Windows
cat module.json | grep requiresCore            # Linux
```

После установки (до включения) удобнее одной командой:

```bash
npm run modules:status
```

Она показывает `Совместимость: OK` или `НЕ СОВМЕСТИМ` и причину.

## 2. Установить пакет модуля

Модуль должен попасть **в два места**: backend (загрузчик) и сборка фронта (Vue-компоненты).
Способы:

### 2.1. npm-пакет (штатный)

```bash
npm i @isar/<code>@<version>
npm run build:v3        # фронт модуля попадает в общий бандл (vite alias)
```

Для приватного registry — `.npmrc` с токеном **только на сборочной машине/в CI**
(не коммитить, не класть в образ). Координаты пакета и версию берёт у поставщика;
версия также указана в `package.json`/`module.json` модуля.

```ini
@isar:registry=https://npm.example.com/
//npm.example.com/:_authToken=${NPM_TOKEN}
```

### 2.2. Каталог `modules/<code>` (zip/артефакт)

```
modules/
  <code>/
    module.json        # или legacy manifest.json
    index.js           # backend-вход
    frontend/          # Vue-компоненты (нужны на сборке фронта)
```

`modules/*` в `.gitignore`: платный код в репозиторий не коммитится.

### 2.3. Docker

Образ собирается из этого репозитория (`infra/common/dockerfile`), поэтому:

- каталог `modules/` копируется в **обе стадии** (frontend build + runtime) — уже сделано в Dockerfile;
- при установке через npm нужен `.npmrc` и токен на этапе `npm install` (build secret / `--build-arg`);
- переменные окружения задаются в `env_file`/`environment` compose, а **не** в образе.

Пример (demo, `infra/demo/env.demo`):

```env
ENABLED_MODULES=<code>
SYS_MODULE_<code>_LICENSE=<payload>.<signature>
SYS_MODULE_LICENSE_PUBLIC_KEY=<PEM>
SYS_INSTANCE_ID=<стабильный id инсталляции>
```

> **Проверка после установки:** `npm run modules:status` должен показать
> `Пакет: <путь>` и `Манифест: module.json|legacy manifest.json`.

## 3. Миграция: отдельно запускать не нужно

Таблица `archrep.isar_modules` и параметры группы «Модули» (`SYS_MODULE_<code>_ENABLED`,
`DRAWIO_MXFILE_MAX_MB`) создаются **штатным деплоем ядра** — миграция входит в состав релиза
(demo: `npm run db:migrate` в составе деплоя; prod: `psql -f DB/scripts/migrate_20261103120000_isar_modules.sql`
в составе выкладки). Установка модуля **не требует** запуска миграций ядра.

Задача администратора — только убедиться, что ядро актуально:

```sql
select to_regclass('archrep.isar_modules');   -- имя таблицы, не NULL
```

Если `NULL` — на стенде старый релиз ядра: сначала обновите ядро, затем возвращайтесь
к установке модуля. Ручной прогон скрипта (идемпотентен) допустим только как восстановление:

```bash
psql "$DB_URL" -f DB/scripts/migrate_20261103120000_isar_modules.sql
```

Проверка после деплоя:

```sql
select code, description, value, value_type, "group" from archrep.ar_settings_parameters
 where code like 'SYS_MODULE_%' or code = 'DRAWIO_MXFILE_MAX_MB';
```

## 4. Настроить окружение

Файл: `.env.development` / `.env.production` (локально) или `env_file` compose (demo/prod).
Приоритет значений в ядре: **env → БД → дефолт**.

| Переменная | Обяз.? | Назначение |
|---|---|---|
| `ENABLED_MODULES` | да (или альтернатива ниже) | список кодов через запятую — **аварийный override**: перечисленные включаются, остальные выключаются |
| `SYS_MODULE_<code>_ENABLED` | альтернатива | точечное включение одного модуля (`true`/`false`) |
| `SYS_MODULE_<code>_LICENSE` | если лицензия обязательна | ключ; **только env**, в БД и на фронт не попадает |
| `SYS_MODULE_LICENSE_PUBLIC_KEY` | если ключ подписан | публичный ключ Ed25519 (PEM или base64 от PEM) |
| `SYS_INSTANCE_ID` | **рекомендуется** | стабильный id инсталляции для привязки ключа |
| `MODULES_DIR` | нет | альтернативный каталог модулей (по умолчанию `<repo>/modules`) |
| `SYS_MODULE_LICENSE_ALLOW_UNVERIFIED` | только тест | `true` — не проверять подпись (запрещено на prod) |

**Про `instance_id`.** По умолчанию он вычисляется как `<hostname>:<DB_NAME>` — при смене
хоста или имени БД лицензия «отвалится», а на двух серверах с одинаковыми hostname/DB_NAME
значение совпадёт. Перед выпуском ключа сгенерируйте уникальный и больше не меняйте:

```bash
npm run modules:status -- --new-instance-id    # → SYS_INSTANCE_ID=<uuid>
```

```env
SYS_INSTANCE_ID=8f14e45f-...
```

Текущее значение показывает `npm run modules:status` (строка `instance_id:`); если переменная
не задана, диагностика выводит предупреждение.

**Коды в именах переменных:** код модуля подставляется **буквально, строчными буквами**,
дефисы заменяются на подчёркивания:

| Код модуля | Переменная включения | Переменная ключа |
|---|---|---|
| `drawio-pro` | `SYS_MODULE_drawio_pro_ENABLED` | `SYS_MODULE_drawio_pro_LICENSE` |
| `tech-radar` | `SYS_MODULE_tech_radar_ENABLED` | `SYS_MODULE_tech_radar_LICENSE` |

Это правило контракта (`docs/modules-contract.md` §14 «Соглашения»): имя переменной однозначно
выводится из кода, таблица соответствий не нужна. Вариант `SYS_MODULE_DRAWIO_PRO_ENABLED`
ядро **не читает**.

### 4.1. Ограничения лицензионного гейта (важно понимать)

> **Решение (2026-11-02): проверка лицензии остаётся офлайн.** Онлайн-активация и лицензионный
> сервер не вводятся; перечисленные ниже ограничения приняты осознанно
> (`docs/modules-contract.md` §16.3).

Проверка лицензии **офлайн** (контракт §16.3), поэтому:

| Ограничение | Следствие | Что делать |
|---|---|---|
| `instance_id` самообъявленный | скопировав ключ **и** `SYS_INSTANCE_ID` на второй сервер, там тоже получите активную лицензию | выдавать ключ под конкретный стенд, фиксировать `instance_id` в акте/заявке, считать копирование нарушением лицензии |
| Нет счётчика инсталляций | ядро не узнает, что ключ используется дважды | при необходимости — онлайн-активация (вне текущего решения) или аудит поставщиком |
| `exp` проверяется по часам сервера | перевод часов назад продлевает срок | синхронизация времени (NTP) — требование эксплуатации |
| Ключ в env | доступ к env = доступ к ключу | ограничить доступ к файлу/секрету, не логировать env |

`instance_id` **не является** криптографической защитой от копирования: его задача — исключить
случайное совпадение и привязать ключ к заявленному стенду. Полная защита возможна только
онлайн-проверкой, которая противоречит принятому решению «проверка офлайн».

**Альтернатива env — параметр БД:** «Настройки → Параметры», группа «Модули»,
код `SYS_MODULE_<code>_ENABLED` (после изменения — перезапуск API: параметры кэшируются).
Значение из env всегда важнее.

## 5. Включить модуль

Достаточно одного из:

1. `ENABLED_MODULES=<code>` (перечисление — авторитетно: всё, чего нет в списке, выключено);
2. `SYS_MODULE_<code>_ENABLED=true`;
3. `update archrep.isar_modules set enabled = true where code = '<code>';`
   (строка появляется после первого старта с установленным модулем).

Порядок приоритета: env-override → `isar_modules.enabled` → параметр БД → `false`.

## 6. Перезапустить API и убедиться, что модуль поднялся

```bash
npm start                 # локально
# или: docker compose -f infra/demo/docker-compose.yml up -d --build
```

Ожидаемые строки в логе:

```
[modules] версия ядра 1.0.0; кандидаты: <code>
[modules][<code>] маршруты смонтированы ядром (адаптер handlers): N/N
[modules] активно: <code>
```

Если модуль использует legacy-манифест — будет предупреждение
`используется legacy manifest.json …` (это нормально до приведения модуля к контракту).

Проверки:

```bash
npm run modules:status
```

```bash
curl -s <BASE_URL>/api/config | jq '.modules'
# { "<code>": { "enabled": true, "licensed": true, "edition": "standard", "expires_at": "2027-01-01" } }
curl -s <BASE_URL>/api/<code>/manifest | jq '{active, enabled, licensed, reason}'
```

```sql
select code, version, core_version, enabled, licensed, license_expires_at
  from archrep.isar_modules order by code;
```

`GET /api/config.modules` — **источник правды для UI**: по нему фронт решает, показывать ли
кнопки/панели модуля. `/api/<code>/manifest` — вспомогательный (в нём есть `reason`).

## 7. Выдать права ролям

Модуль объявляет права в манифесте (`permissions[]`, для DrawIO Pro — `drawio_pro:manage`).
Они должны быть в каталоге ядра (`backend/auth/permissionsCatalog.js`) — это делает разработка ядра.
При каждом старте API `bootstrapAuth` **досоздаёт** права каталога ролям (для `SYSTEM_ADMIN` — полный
набор, для остальных — недостающие, без удаления существующих).

Как выдать:

1. **Автоматически:** перезапустить API — `ARCHITECT`/`REPOSITORY_ADMIN`/`SYSTEM_ADMIN`
   получат право из каталога.
2. **Точечно:** «Администрирование → Роли» → роль → отметить право → «Сохранить».

> ⚠️ Сохранение роли в UI **заменяет** весь набор прав роли. Если после сохранения право
> «пропало» — перезапустите API (bootstrap вернёт права каталога) или отметьте нужное сразу в UI.

Проверка для текущего пользователя:

```bash
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:3000/api/auth/me | jq '.permissions'
```

## 8. Проверить в UI

| Что | Где | Ожидание |
|---|---|---|
| Кнопка/панель модуля | форма заключения → блок «Схемы» | видна только при `enabled && licensed` и праве |
| Панель модуля | редактор схемы (открывается кнопкой модуля) | панель слева, iframe Draw.io справа |
| Отсутствие модуля | — | кнопки нет (не «серая»), API модуля отвечает 402/403 |

Проверка API-гейта вручную:

```bash
curl -s -o /dev/null -w "%{http_code}\n" -X POST <BASE_URL>/api/<code>/parse \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"mxfile":"<mxfile/>"}'
# 200/400 — модуль активен; 402 — нет лицензии; 403 — модуль выключен или нет права
```

## 9. Обновление модуля

1. Заменить пакет: `npm i @isar/<code>@<new>` или распаковать новую версию в `modules/<code>`.
2. `npm run build:v3` — **если менялся фронт** модуля.
3. Сверить `requiresCore` новой версии с ядром (шаг 1). При несовместимости модуль не запустится,
   а предыдущая версия уже заменена — держите архив предыдущей версии.
4. Перезапустить API; проверить `version` в `isar_modules` и `modules:status`.
5. Лицензия обычно переносится (привязана к инсталляции, не к версии). Если ключ новый —
   заменить `SYS_MODULE_<code>_LICENSE` и перезапустить.

Откат: вернуть предыдущий пакет, пересобрать фронт, перезапустить. Версия в реестре обновится.

## 10. Отключение и удаление

**Временно отключить (код остаётся):**

```env
ENABLED_MODULES=            # убрать код из списка
# или
SYS_MODULE_<code>_ENABLED=false
```

или `update archrep.isar_modules set enabled = false where code = '<code>';` → перезапуск API.
Маршруты модуля перестают монтироваться, UI скрывается, данные ядра не затрагиваются.

**Удалить полностью:**

1. Отключить (см. выше) и перезапустить.
2. Удалить пакет: `npm rm @isar/<code>` / удалить `modules/<code>`; `npm run build:v3`.
3. Удалить запись реестра: `delete from archrep.isar_modules where code = '<code>';`
4. Схема модуля `archrep_mod_<code>` — удаляется только если модуль её создавал.
   У DrawIO Pro своей схемы нет. Автоматического `--drop-schema` пока нет
   (`docs/modules-contract.md` §16.7, вопрос 4): удаление данных модуля — отдельным согласованным
   действием DBA (резервная копия обязательна).

## 11. Диагностика: симптом → причина → действие

| Симптом | Причина | Что сделать |
|---|---|---|
| В логе нет строк `[modules]` | старый код ядра / модуль не установлен | проверить версию ядра; `npm run modules:status` |
| `[modules] <code>: пакет не найден` | пакет не в `node_modules` и нет `modules/<code>` | установить пакет (шаг 2); проверить `MODULES_DIR` |
| `requires core X, have Y` | модуль новее ядра | обновить ядро или поставить совместимую версию модуля |
| `манифест невалиден` | битый/неполный `module.json` | запросить у поставщика корректный артефакт |
| `используется legacy manifest.json` | модуль на старом манифесте | нормально; задача модулю — перейти на `module.json` |
| `таблица archrep.isar_modules не найдена` | ядро на старом релизе (миграция входит в деплой) | обновить ядро штатным деплоем — §3 |
| `/api/config.modules` пуст | модуль не найден/не включён | шаги 2 и 5; проверить лог |
| `enabled: true, licensed: false` | нет/просрочен/чужой ключ | `modules:status` → строка `Лицензия`; запросить ключ на нужный `instance_id` |
| `публичный ключ не настроен` | не задан `SYS_MODULE_LICENSE_PUBLIC_KEY` | задать PEM; либо (только тест) `ALLOW_UNVERIFIED=true` |
| `подпись ключа недействительна` | ключ испорчен/от другого продукта | запросить ключ заново |
| `ключ привязан к другой инсталляции` | другой `instance_id` | задать стабильный `SYS_INSTANCE_ID` и запросить ключ под него |
| Кнопка модуля не видна | нет лицензии / нет права / UI в кэше | `/api/config` + `/api/auth/me`; перезагрузить страницу |
| `403` на маршруте модуля | модуль выключен или нет права | `modules:status`; шаг 7 |
| `402` на маршруте модуля | нет активной лицензии | шаг 4 (ключ) |
| `409` при сохранении схемы | устаревшая версия (оптимистичная блокировка) | переоткрыть схему и повторить |
| Сборка фронта падает на модуле | CommonJS/алиасы | `npm run build:v3` с логом; проверить `vite.config.js` (`commonjsOptions`) |
| `docker build` → `failed to calculate checksum ... "/modules": not found` | в архив деплоя не попал каталог `modules/` (deploy.bat собирает явный список путей) или его нет в контексте сборки | обновить `infra/prod/deploy.bat` / `infra/demo/deploy.bat` (там уже условное добавление `modules`); убедиться, что `modules/.gitkeep` на месте; при ручной сборке — создать `modules/` |

**Одна команда для всего перечисленного:** `npm run modules:status` (код выхода 1 — есть проблемы).

## 12. Чего делать нельзя

- Класть ключ лицензии в БД, `settings_json`, git, образ, логи или на фронт — **только env**.
- Включать `SYS_MODULE_LICENSE_ALLOW_UNVERIFIED=true` на prod (отключает проверку подписи).
- Коммитить код платного модуля (каталог `modules/*` в `.gitignore`).
- Патчить код модуля в ядре — несовпадения закрываются адаптерами ядра
  (`docs/modules-contract.md` §16.6) или задачей репозиторию модуля.
- Давать модулю доступ к таблицам ядра напрямую — только через `ctx` (контракт §6.1).
- Менять `SYS_INSTANCE_ID` после выпуска ключа (лицензия перестанет действовать).

## Приложение А. Прогон инструкции на модуле DrawIO Pro (0.1.0)

**Условия прогона:** ядро `1.0.0`; модуль — реальный чекаут `dgabadulin/isarDiagramEditor`
(подключён как `modules/drawio-pro` через junction в `C:\Temp\isar-mods` + `MODULES_DIR`);
БД в среде прогона недоступна (`ENOTFOUND`), поэтому шаги, требующие БД, помечены отдельно.

### А.1. Что прошло

### А.3. Пробелы, найденные прогоном, и что исправлено

| # | Пробел | Исправление |
|---|---|---|
| 1 | `infra/common/dockerfile` не копировал `modules/` → в контейнере модуля нет, фронт собирался с заглушкой | `COPY modules` в стадию сборки фронта и в runtime-образ |
| 2 | `.gitignore` разрешал случайно закоммитить платный код | `modules/*` + `!modules/README.md` |
| 3 | legacy-манифест без `license` → платный модуль считался бесплатным | legacy-адаптер fail-closed: `license.required = true` |
| 4 | Не было способа проверить подключение одной командой | `npm run modules:status` (пакет, манифест, совместимость, лицензия, RBAC, реестр, `instance_id`) |
| 5 | Установленный-но-выключенный модуль делал диагностику «красной» | проблемы только для включённых модулей, остальное — предупреждения (код выхода 1 только при проблемах) |
| 6 | `instance_id` по умолчанию зависел от `DB_NAME` (тихая поломка лицензии) | в инструкции — обязательная рекомендация задать `SYS_INSTANCE_ID`; значение печатает `modules:status` |
| 7 | Для нового модуля (не drawio-pro) в ядре нет RBAC-правила | диагностика явно показывает `НЕ ПОКРЫТ RBAC`; правило добавляется в ядре при интеграции (бэклог: генерация из манифеста) |
