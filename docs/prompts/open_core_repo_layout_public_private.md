# Промпт: Open Core с платными private-модулями

## Контекст

- **Проект/репозиторий:** ИСАР, планируется свободное распространение ядра и коммерциализация отдельных модулей.
- **Текущая идея:** открыть основной репозиторий на GitHub, а часть функционала (RBAC Pro, DrawIO Pro и т.п.) продавать.
- **Ограничения:** платные модули не должны быть доступны для свободного скачивания в public-репозитории.

## Цель

Определить правильную организацию GitHub-репозиториев и поставки артефактов, чтобы одновременно сохранить open-source модель для ядра и защитить коммерческие модули.

## Промпт для ИИ (скопировать в чат)

```
Помоги спроектировать модель Open Core для проекта ИСАР:

Условия:
1) Ядро должно быть свободно-распространяемым (public GitHub).
2) Часть модулей должна быть платной и недоступной для скачивания из публичного репозитория.
3) Нужно понять, где физически хранить код платных модулей и как их подключать к ядру.

Ответь:
- Можно ли держать платные модули в том же public-репозитории и "скрыть" их?
- Какой вариант лучше: отдельные private-репозитории, private packages, отдельные Docker-образы?
- Как организовать структуру репозиториев (пример имен и назначений)?
- Как сделать лицензирование и активацию модулей (без тяжелого DRM)?
- Какие риски (технические/юридические/операционные) и как их снизить?

Дай практическую рекомендацию для MVP на 1-2 месяца.
```

## Формат ответа

- Краткий вывод "что делать / чего не делать".
- Рекомендуемая схема репозиториев (public core + private modules).
- Варианты поставки (packages/images) с плюсами и минусами.
- Минимальный план внедрения (по шагам).
- Ключевые риски и mitigation.

## Критерии готовности

- Однозначно объяснено, что в public-репозитории нельзя скрыть часть кода.
- Предложена рабочая модель Open Core с private-модулями.
- Зафиксирована целевая структура GitHub-репозиториев.
- Описан способ дистрибуции и активации платных модулей.
- Сформирован краткий MVP-план внедрения.
