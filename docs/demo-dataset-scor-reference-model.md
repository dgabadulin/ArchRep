# Демо-набор данных (референтная модель SCOR) для насыщенной demo-модели

**Основание:** целевые объёмы и ключевые связи — [`demo-full-model-entities-matrix.md`](demo-full-model-entities-matrix.md) **§2** (строки 1–15 §1 в объёме demo). Сущности **§2.1** в репозитории пока не представлены — в конце даны только **ориентиры** для будущего расширения.

**Референтная модель:** [SCOR](https://www.supply-chain.org/scor) (Supply Chain Operations Reference). Ниже процессы SCOR отражаются в **`business_function` уровня L1**; **клиентские платные продукты и услуги** — в **`business_service`**.

**Сценарий:** вымышленный холдинг **«СеверЛогистик»** (B2B-логистика, 3PL, контрактное производство СТМ, дистрибуция для торговых сетей). Имена — для демонстрации.

---

## Термины (согласованные поправки)

### 1. Бизнес-сервис (`business_service`)

**Бизнес-сервис** — это **продукты и услуги, которые компания предоставляет своим клиентам за деньги** (внешний коммерческий оффер: контракт, тариф, подписка, разовая услуга).  
Не путать с внутренними возможностями оргструктуры или «функциями для себя»: внутреннее планирование, MDM «для себя», ИТ-сервис **без выставления счёта внешнему клиенту** — оформляются через **`business_function`** и/или **`system`**, а не как отдельный платный `business_service`, если только компания **не продаёт** эту услугу на рынок.

### 2. Бизнес-функции (`business_function`) и SCOR

- Процессы **SCOR** в демо-модели — это **`business_function` уровня L1** (домены): типовые **Plan, Source, Make, Deliver, Return**, плюс сквозной домен **Enable** (обеспечение цепочки: ИТ, качество, HR, архитектура и т.п.).
- **Все остальные бизнес-функции** (бизнес-способности) — это **L2, L3 и далее** в иерархии `parent_id`: дочерние узлы под соответствующим доменом L1.

### 3. Партнёры (`partner`)

В справочник **`partner`** входят **все внешние контрагенты**, в том числе:

- поставщики и исполнители по **цепочке поставок** (сырьё, логистика, упаковка, лаборатории, банк, ЭДО и т.д.);
- **поставщики ИТ-решений** (вендоры ПО и платформ);
- **интеграторы** (внедрение, проекты);
- **партнёры сопровождения / поддержки** (support, аутсорс эксплуатации).

Связи с ИС/модулями/технологиями — через FK и проекции §3.2 (`system_partner_*`, `subsystem_partner_*`, `technology_partner_vendor`).

### 4. Принцип (`principle`) vs ADRP (`adr_principle`)

- **`principle` (`ar_principles`)** — **верхнеуровневые архитектурные принципы компании**: долгоживущие правила уровня политики/стратегии, задающие рамки для решений и для ADRP.
- **`adr_principle` (ADRP)** — **прикладные архитектурные принципы** («далее поступаем так в предметной области…»): конкретизация под цепочку поставок, интеграции, данные SKU и т.п. (то, что ранее ошибочно было перечислено в разделе «принципы» настоящего документа, относится сюда).

Примеры **корпоративных** `principle`: первичность архитектурных принципов; импортозамещение; соблюдение законодательства; **данные — актив компании**; единая технологическая политика; кибербезопасность по умолчанию; устойчивое развитие и экология — и т.д.

## 1. Соответствие SCOR, уровней BF и артефактов

| Домен SCOR (L1 `business_function`) | Смысл | Типичные клиентские `business_service` (платные внешние услуги) | Внутренние опоры |
| ----------------------------------- | ----- | -------------------------------------------------------------- | ----------------- |
| **Plan** | Планирование цепочки | Консалтинг S&OP, подписка на прогнозную аналитику для клиента | ИС планирования, `integration_flow` |
| **Source** | Закупки и поставщики | Услуги тендерного сопровождения для клиента (если продаются) | ERP закупок, портал поставщика |
| **Make** | Производство / переработка | Контрактное производство СТМ, слот мощности | MES, LIMS |
| **Deliver** | Логистика и доставка | 3PL-хранение, доставка «до двери», экспресс-тариф | WMS, TMS, OMS |
| **Return** | Возвраты | Реверс-логистика и утилизация как коммерческая услуга | Модуль возвратов |
| **Enable** | Обеспечение цепочки | *(Только если продаётся внешнему заказчику, напр. аудит или обучение)*; иначе — в основном **внутренние** BF L2/L3 и ИС | Каталог ИС, IAM, Service Desk |

## 5. Бизнес-функции (`business_function`) — **L1 = SCOR**, **L2/L3+** — детализация

### 5.1 Уровень L1 (ровно 6 доменов — процессы SCOR + Enable)

| L1 (код для demo, пример) | Наименование домена |

| BF-L1-P | Планирование цепочки поставок (**Plan**) |
| BF-L1-S | Закупки и управление поставщиками (**Source**) |
| BF-L1-M | Производство и выпуск (**Make**) |
| BF-L1-D | Доставка и складская логистика (**Deliver**) |

### 5.2 Уровни L2, L3 (примеры дочерних `business_function`)

| Родитель L1 | Примеры L2 | Примеры L3 (под L2) |
|-------------|------------|---------------------|
| **P** | Прогноз спроса; Баланс запасов; Портфель заказов поставщикам | «Согласование прогноза с сетью» (L3 под «Прогноз спроса»); «Расчёт целевого уровня запасов РЦ» (L3 под «Баланс запасов») |
| **S** | Тендер; Контракт; Входной контроль поставки | «Оценка риска однопоставщиковости» (L3); «Согласование условий поставки» (L3) |

| **R** | Регистрация возврата; Разбор причин; Утилизация | «Оформление претензии поставщику упаковки» |
| **E** | Архитектура ИТ; Управление инцидентами; Обучение; Комплаенс | «Ведение реестра интеграций ИС»; «Архитектурное согласование изменений» |

## 9. Интеграционные потоки (`integration_flow`) — **≥115** направлений (укрупнённо)

**Явные 80** по таблицам **§17.4–17.7** (по **20** записей на каждый код проекции `integration_flow` / `integration_flow_system_module` / `integration_flow_module_system` / `integration_flow_module_module`) задают минимальный объём `ar_integration_flows` для демо после импорта.

**Первые 35** (базовый укрупнённый набор):

1. OMS → WMS: заказ на отбор.  
2. WMS → TMS: задание на отгрузку и маршрут.  
3. TMS → OMS: статус доставки и POD.  
4. MES → ERP: выпуск партии.  
5. MDM → OMS / WMS: SKU и штрихкоды.  
6. ESB: нормализация события «Отгрузка» для BI.  
7. Портал поставщика → ERP: подтверждение поставки.  
8. WMS Москва ↔ WMS Казань: межскладской трансфер.  
9. Data Lake ← ERP / WMS: срезы для S&OP.  
10. Service Desk → мониторинг: инцидент по SLA интеграции.  
*(До 35 — вариации по магазинам, ночные пакеты, обратные статусы.)*

**Ещё 35** (второй контур — отдельные площадки, тестовые контура, аварийный обход шины): дублирование топологии с другими `id` потоков.

Итого целевой минимум для демо-репозитория: **80 + 35 = 115** строк в `ar_integration_flows` (плюс вариации по сети магазинов при необходимости).

## 13. Архитектурные принципы компании (`principle`) — **9** верхнеуровневых

| № | Формулировка (для `ar_principles`) |
|---|-----------------------------------|
| 1 | **Первичность архитектурных принципов** — решения по ИС и интеграциям не противоречат утверждённым принципам без явного пересмотра |
| 2 | **Импортозамещение** — приоритет отечественных решений там, где это допустимо по регуляторике и TCO |
| 3 | **Соблюдение законодательства** — персональные данные, прослеживаемость, отраслевые нормы соблюдаются по умолчанию в проектировании |
| 4 | **Данные — актив компании** — качество, владение и доступность данных наравне с ИС |
| 5 | **Единая технологическая политика** — стек, шины, стандарты API согласованы на уровне компании |
| 6 | **Кибербезопасность по умолчанию** — защищённость и контроль доступа не «добавляются потом» |

## 20. Критерии готовности demo-набора

- **`business_service`** — только **внешние платные** продукты/услуги.  
- **`business_function`**: **L1 = SCOR**, нижние уровни — **L2+**.  
- **`partner`** включает **ИТ-вендоров, интеграторов и поддержку**.  
- **`principle`** — **корпоративные** архпринципы; **ADRP** — **прикладные**.  
- Есть **таблица конкретных связей** (§17) для проверки графа и импорта; **сводка по всем типам связей §3.1–§3.2** — в **§21**.  
- Каждая корневая ИС из **§6 / §17** имеет **≥1** связи `system_business_service` и **≥1** `system_business_function`; по **каждому** коду типа из §21 — **≥10** экземпляров: либо **явные строки §17** (N в §21), либо **≥10 заполненных FK** для типов с пометкой «только FK» в §21. Для четырёх проекций интеграционных потоков — **по 20** явных пар в **§17.4–17.7**.  
- Записей в `ar_integration_flows` для демо — **не менее 115** (§9): **80** из явных таблиц §17.4–17.7 + **35** укрупнённого контура; допускаются ещё вариации по магазинам и тестовым контурам.
