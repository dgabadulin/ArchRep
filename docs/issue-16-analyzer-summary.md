## Пункт 16 — Системы с parent_ar_systems_id как отдельная сущность

**Формулировка:** «Системы у которых есть значение в поле parent_ar_systems_id в компоненте Анализатор считать отдельной сущностью» (в issue — «не проверено»).

**Смысл:** такие системы должны отображаться как отдельный тип сущности — **system_child** (другая иконка и подпись; в `entityTypeConfig` уже есть `system_child`).

**Текущее состояние:**
- При **первичном построении** графа выбранные объекты берутся из списка; для систем с `parent_ar_systems_id` уже выставляется `displayType = 'system_child'` (в `AnalyticsView.vue`), поэтому изначально выбранные дочерние системы отображаются отдельной сущностью.
- Узлы, **добавляемые через «Добавить связи»**, создаются в `relationsToGraphData` из полей связи (`from_entity_type` / `to_entity_type`). В API приходит только `'system'`, поэтому при раскрытии связей все системы отображаются одним типом.

**Предлагаемый план (без изменений бэкенда):**
1. Расширить **`resolveNodeNames`** в `AnalyticsView.vue`: для узлов с `entityType === 'system'` при подстановке имени через `fetchEntity` проверять в ответе поле `parent_ar_systems_id`; если оно задано — при обновлении узла выставлять `entityType: 'system_child'` вместе с обновлением `name`.
2. Дополнительных запросов не требуется — используется уже получаемый объект системы в `fetchEntity`.
3. Та же логика должна поддерживаться в актуальном `AnalyticsView.vue` (без альтернативного G6-экрана).

Итого: одна правка в `resolveNodeNames` — при обновлении имени для узлов типа `system` дополнительно выставлять `entityType: 'system_child'`, если в ответе API есть `parent_ar_systems_id`.

### «Не проверено»

**3. Отображение связей различных типов** (система–система, система–техкомпонент, система–сервер, система–функция, функция–процесс, АР–система, АР–интеграция, система–бизнес-домен и т.д.)

- Сейчас в граф попадают только связи метамодели из `togafApi.relations()` (включая ИС–технологию `system_technology` и проекции интеграционных потоков `integration_flow*` из `ar_metamodel_relations`).
- Остальные типы зависят от того, возвращает ли API метамодели их в `togafApi.relations()` в формате `from_entity_type` / `to_entity_type` / `relation_type`.
- Действие: проверить по данным и списку типов связей в UI, что все нужные типы приходят в `loadAllRelations()` и отображаются; при отсутствии — доработать бэкенд или маппинг в `graphApi.js`.

**4. Передача данных в компонент без показа выбора объектов**

- Сейчас компонент всегда показывает пикер (тип сущности, список, «Построить граф»), затем граф.
- Требование: режим «передали готовые nodes/edges — показываем только граф, без пикера».
- Реализация: опциональные props у страницы/компонента (`initialNodes`, `initialEdges`, `initialRelations`); при их наличии не рендерить пикер, сразу выставлять `graphBuilt = true` и подставлять переданные данные. Тогда вкладка «Зависимости» на форме системы (п.11) сможет рендерить тот же `AnalyzerGraph` с заранее собранными узлами/рёбрами для одной системы.

### «Не сделано» / «на паузе»

**6. Анимация появления новых связей (раскрываться по очереди)**  
В задаче помечено «пока на паузе». В коде анимации нет: при «Добавить связи» узлы/рёбра добавляются разом. При возобновлении — добавлять новые узлы/рёбра по одному или пакетами с задержкой и при необходимости обновлять раскладку/фит после каждого шага.

**15. При построении графа по одному объекту — раскладка «звезда», объект в центре, связанные вокруг**

- В коде уже реализовано: при `ids.length === 1` вызывается `applyLayout('star', centerId)`.
- В issue указано «не сделано, объект выносится только один без связей» — возможно, по выбранной системе в БД нет связей или баг в данных/формате ответа.
- Действие: проверить на системе с заведомо существующими связями; если соседи появляются и звезда строится — п.15 считать выполненным, в issue уточнить, что проблема была в данных.

### «Сделано, надо исправить»

**19. При раскрытии связей — центрировать и масштабировать граф; только уменьшать масштаб, чтобы весь граф помещался; не делать значки слишком крупными**

- Файлы: `AnalyzerGraph.vue` (configs.view.maxZoomLevel, fitToContents с getViewBox/setViewBox).

### «Не сделано» → сделано

**22. При раскрытии связей вершины — не накладывать новые узлы на существующие; при перекрытии отодвигать раскрываемую вершину (удлинить ребро) и раскладывать её связи по «звезде»**

- Реализовано: при «Добавить связи» по узлу A вызывается **applyLayoutForAddedLevel(A, addedNodeIds)**. Текущие позиции берутся из графа; для A и новых соседей считается раскладка «звезда» (A в центре, соседи по окружности радиусом 180). Если позиции пересекаются с уже нарисованными узлами (расстояние < 65px), центр A сдвигается в сторону от «чужих» узлов (сумма направлений от них), раскладка звезды пересчитывается; цикл до 20 итераций или пока нет пересечений. В граф записываются только позиции A и новых узлов, остальные не трогаются.
- Файлы: `AnalyzerGraph.vue` (applyLayoutForAddedLevel), `AnalyticsView.vue` (onAddLevel передаёт список добавленных id и вызывает applyLayoutForAddedLevel, затем fitToContents).
